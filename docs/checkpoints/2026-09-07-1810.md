Recurring architectural theme (explicitly called out by rounds 3 and 4's own review text): `src/parser/inline.rs` has THREE overlapping hand-written state machines — `scan_inline_closer`, `find_matching_close`, `split_top_level` (plus its `_fast` variant) — each independently tracking scope/key/value/quote/raw/escape/whitespace state with slightly different mechanisms, and each round of review has found a genuine defect in one of them that the others either already had fixed correctly or hadn't needed to address yet. Both reviews recommend eventually unifying these into one shared state machine, but explicitly say that unification should come AFTER semantic correctness is achieved, not be attempted as part of a bug-fix task — I have consistently followed that guidance and declined to do the unification within any of these tasks, instead fixing each defect narrowly and noting the unification opportunity in my own task descriptions for future reference. Given the pattern (4 rounds, 4 new P2s each round, all in the same file), it would not be surprising if a round 5 finds more defects in this same area — if that happens, the same decomposition pattern (reproduce myself first, read the exact current code, write a self-contained task description with root cause already diagnosed, sequential `/wrush` worktrees, zero-trust verify, cherry-pick) should be repeated.
