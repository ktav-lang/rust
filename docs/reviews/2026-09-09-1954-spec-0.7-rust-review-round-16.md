## Найденные Проблемы

### R16-F1. P2: `Some` разрешён как ключ при записи, но отсутствует при чтении

Места: `src/de/key_deserializer.rs:163`, `:164`;
`src/ser/text_serializer.rs:562`.
Пробел в тестах: `tests/ser/key_name_consistency.rs:161`.
Заявленный serde roundtrip: `README.md:206`.

Общий `KeyOnlySer` явно принимает `Some`, делегируя сериализацию
внутреннему значению. Но `KeyDeserializer` перенаправляет
`deserialize_option` в `deserialize_any`, который вызывает строковый
visitor. В serde 1.0.228 `OptionVisitor` принимает `visit_some`,
`visit_none` или `visit_unit`, а не строку. Поэтому успешно записанный
map нельзя восстановить в исходный тип ни одним из read API.

Минимальный воспроизводитель:

```rust
use std::collections::BTreeMap;

type Map = BTreeMap<Option<u32>, String>;
let source = Map::from([(Some(42), "v".to_owned())]);
let text = ktav::to_string(&source).unwrap();
assert_eq!(text, "42: v\n");
let thin = ktav::from_str::<Map>(&text);
let owned = ktav::de::from_value::<Map>(ktav::ser::to_value(&source).unwrap());
assert_eq!(thin.unwrap(), source);
assert_eq!(owned.unwrap(), source);
```

Оба результата чтения:
`Err(Message("invalid type: string \"42\", expected option"))`.
Та же ошибка возникает при `from_value(parse(text))` и при чтении
текста, полученного через `render(to_value(source))`.

Проверены `Some(u32)`, `Some(bool)`, `Some(char)`, `Some(u128::MAX)`,
`Some(newtype)`, `Some(unit enum)`, `Some(String("null"))` и вложенный
`Some(Some(u32))`. Все восемь успешно записываются обоими writers;
разобранные документы совпадают. Все четыре комбинации чтения
каждого варианта дают ошибку: 32 из 32 в debug и в release.
Отдельные обязательные assertions thin- и owned-roundtrip действительно
падают в обоих профилях. Это внешние воспроизводители, не штатные тесты.

Новый `some_and_char_and_unit_variant_keys_match` проверяет только
полученное имя после записи. Он не десериализует результат в Option,
поэтому штатный набор остаётся зелёным.

Исправление: реализовать `deserialize_option` через `visitor.visit_some(self)`
и убрать `option` из forwarding-макроса. Имя ключа всегда существует;
его текст `null` не должен становиться `None`: по §5 имена Object есть
строки, а не scalar values. Сохранить writer-отказ для `None` и
`Some(None)`, который контроль уже подтверждает на обоих путях.
Добавить inverse-матрицу обоих readers и writers, включая вложенные
Some, newtype, enum и буквальное имя `null`.

### R16-F2. P3: временный String лишает короткие ключи inline fast path

Места: `src/ser/text_serializer.rs:481`, `:488`, `:489`, `:491`, `:506`;
`src/ser/map_serializer.rs:22`.
Прежний scalar-путь: `src/ser/value_serializer.rs:149`.

`serialize_key_name` создаёт пустой `String`, пишет туда имя, затем
конвертирует его в `Scalar`. Для обычного непустого короткого имени
вроде `port` это запрос heap-буфера, копирование в inline Scalar и
освобождение временного буфера. Проверена именно закреплённая
compact_str 0.9.0: `From<String>` вызывает `Repr::from_string(s, true)`
и пытается хранить короткую строку inline, а не сохранять её allocation.
На проверенном 64-битном target inline-вместимость равна 24 байтам.

До изменения owned `MapSerializer` для строкового ключа вызывал
`ValueSerializer::serialize_str`: `Value::String(v.into())` сразу
создавал inline Scalar, без промежуточного heap String. Общая политика
ключей нужна, но этот конкретный способ её реализации добавляет
лишние выделения для типичных String-keyed maps в `ser::to_value`.
Для прямого `to_string` временный String существовал и раньше:
там это возможность оптимизации, а не новая allocation-регрессия.
Обычные поля derive-структур идут через `serialize_field`, не этот путь.

При K коротких map-ключах источник содержит Theta(K) лишних временных
выделений; это не утверждение об измеренном числе allocator calls
после оптимизации компилятора. Общая асимптотика записи не меняется;
временные буферы освобождаются по мере обработки, не удерживаются все
одновременно. Timing и проценты ускорения не измерялись.

Исправление: писать общее имя непосредственно в `Scalar` или возвращать
Scalar из `KeyOnlySer`, не проходя через heap String. compact_str 0.9.0
уже реализует `fmt::Write`, так что нативные числа можно форматировать
в тот же inline-буфер. Сохранить существующую Display-политику
Float-имён и обе writer-матрицы; заменять её на нормализацию Float-значений
нельзя. Перед performance-утверждениями проверить короткие и длинные
имена allocation-счётчиком на небольшом выделенном тесте.

### R16-F3. P3: owned String-ключ больше не получает существующий heap-буфер

Места: `src/de/map_access.rs:32`;
`src/de/key_deserializer.rs:41`, `:44`, `:70`.

Новый owned reader передаёт в helper только `key.as_str()`, после чего
вариант `Local` вызывает `visit_str`, включая запрос `deserialize_string`.
В serde 1.0.228 `StringVisitor::visit_str` выполняет `v.to_owned()`.
Длинный heap-backed Scalar поэтому копируется в новый String, пока
исходный буфер ещё жив; затем исходный ключ освобождается.

Прежний путь передавал `key.into_string()` в serde `StringDeserializer`,
который мог вызвать `visit_string` и отдать буфер целевому String.
Для обычного heap-backed Scalar на проверенном x64 compact_str 0.9.0
в `into_string` переносит владение без копирования.

Без unsafe и без нагрузочного цикла проверен один 52-байтовый ключ:
сравнение адреса буфера до и после `Scalar::into_string` подтверждает
сохранение адреса; до и после `from_value::<BTreeMap<String, String>>`
адрес различается, содержимое совпадает. Debug/release дали одинаковый
результат. Это контроль механизма вместе с чтением исходников, не
allocator benchmark и не требование публичного API сохранять адреса.

Для такого ключа длины L вместо передачи буфера O(1) выполняется
O(L) копирование и требуется новый буфер; у всей операции parse/read
асимптотика из-за этого не меняется. Для inline String-ключей прежнее
преобразование в String само требовало allocation. Для numeric-ключей
новый путь, напротив, полезен: теперь нет обязательного `into_string`
перед разбором. Исправление не должно возвращать эту старую издержку.

Рекомендация: позволить общему key adapter владеть Scalar в owned-ветке.
Числовые методы могут разбирать срез, а строковый visitor получать
`visit_string(s.into_string())`. Отделить это владение от borrowed
event-ветки; не выдавать `visit_borrowed_str` для локально живущего
буфера. Добавить отдельные проверки коротких numeric-имён и длинных
owned String-имён, чтобы оптимизация одной группы не ухудшала другую.

Общие key-only адаптеры устраняют дублируемые списки преобразований и
правильно отделяют имена от числовых Value. `deserialize_any` не
угадывает число; преобразования i128/u128 идут напрямую без усечения.
Различие `Borrowed` / `Local` сохраняет корректные времена жизни:
локальный owned-буфер не выдаётся visitor как долговечный borrow.
R16-F3 про копирование, не про нарушение memory safety. Публичные
`from_str` и `from_value` по-прежнему требуют `DeserializeOwned`.

Проверенные обязательства: строковые имена Object (§5), Integer-домен
и нормализация (§5/§5.2), canonical Float (§5.9.8), сохранение имён
при экранировании (§5.9.10), canonical fixed point (§8.3), а также
заявленный serde roundtrip README. Последний имеет пробел R16-F1;
на нормативном parser/writer corpus новых ошибок не найдено.

Для числовых значений повторены прежние 18 typed и 34 Integer Value
проверки с обязательными assertions: ноль ошибок/расхождений. Все
92 Float проверки также прошли, включая биты f32, Value equality,
strict acceptance и canonical idempotence. Debug и release согласованы.

Глобальные структуры данных в этих четырёх исправлениях не менялись.
Прежние кандидаты для профилирования остаются: сортировка C inline-границ
O(C log C) и binary search в `src/parser/inline.rs`, резерв arena по
длине исходника в `src/thin/mod.rs` / `src/thin/event_parser.rs`, две
временные строки scientific-ветки `src/render/canonical.rs:413`.
Это не новые находки и не доказанные bottleneck текущего workload.
Оснований переписывать индекс или обещать глобальное снижение O
по этому diff нет; конкретные новые расходы выделены в R16-F2/F3.
