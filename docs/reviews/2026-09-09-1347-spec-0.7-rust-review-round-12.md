## Найденные Проблемы

### R12-F1. P2: serde и parser создают разные представления одного Float

Места: `src/ser/value_serializer.rs:73`, `:78`;
`src/ser/text_serializer.rs:80`, `:111`, `:124`;
контракт и сравнение: `src/value/value.rs:20`, `:33`, `:84`.

`Value::Float` документирован как канонический shortest-decimal payload
через Ryu. Parser хранит именно эту форму. Но `ValueSerializer` берёт
payload из текстовых `format_f32`/`format_f64`, которые вызывают
`push_float_body`. Этот helper принудительно вставляет `.0` перед
экспонентой, если в мантиссе нет точки. Для текстового вывода такая
форма допустима, но она отличается от нормализованного payload parser.

Воспроизводитель без ручного конструирования некорректного `Value`:

```rust
let source = std::collections::BTreeMap::from([("x", 1e100_f64)]);
let before = ktav::ser::to_value(&source).unwrap();
let text = ktav::emit_canonical(&before).unwrap();
let after = ktav::parse(&text).unwrap();
assert_eq!(after, before);
```

`before` содержит `Float("1.0e100")`, canonical text равен
`x: 1e100\n`, а `after` содержит `Float("1e100")`. Производный
`PartialEq` сравнивает хранимые строки, поэтому значения не равны.
Обычный `render`, не только canonical writer, даёт тот же эффект:
`ser::to_value(&[1e100_f64])` после `render` и `parse` меняет payload
с `1.0e100` на `1e100`.

Дополнительные подтверждённые случаи:

| Исходное число | Payload из `to_value` | Payload после canonical roundtrip |
|---|---|---|
| `f64::from_bits(1)` | `5.0e-324` | `5e-324` |
| `1e-100_f64` | `1.0e-100` | `1e-100` |
| `1e20_f32` | `1.0e20` | `1e20` |
| `1e-20_f32` | `1.0e-20` | `1e-20` |

Это не потеря точности, не flush-to-zero и не неправильный canonical
text. Обратная десериализация в исходный `f64`/`f32` сохраняет биты;
`parse_strict` принимает canonical output. Проблема в согласованности
публичного Rust API: библиотека сама создаёт ненормализованный `Value`,
который меняется при roundtrip и нарушает документированную форму
`as_float`. Сравнение документов через `Value::PartialEq` получает
ложное различие. Нормативный числовой Float из §5 не сохраняет исходное
написание; этот дефект внутреннего представления не следует выдавать
за ошибку числовой конверсии §5.9.8.

Существующие conformance roundtrip начинаются с `parse`, уже давшего
нормализованный payload. Проверки writer в `tests/unrepresentable.rs`
тоже используют подготовленные формы вроде `Float("1e100")`. Они не
проверяют данный переход из `ser::to_value`. Во внешнем воспроизводителе
assertion точного равенства `Value` действительно падает в debug/release;
отдельные проверки числовых битов проходят. Это не flaky-тест.

Исправление: отделить нормализацию хранимого `Float` от оформления
текстового литерала. `ValueSerializer` должен выдавать представление,
совпадающее с parser, с сохранением проверки конечности и принятой
политики преобразования `f32`. Добавить проверки
`to_value -> emit_canonical/render -> parse` для Object и Array,
scientific-форм, subnormal, обоих нулей и обычной десятичной формы.
Не заменять здесь равенство `Value` только сравнением чисел: последнее
уже истинно и не выявляет дефект. Ошибки NaN/Infinity должны сохранить
`NonFiniteFloat`. Такая развязка заодно позволяет не материализовать
промежуточный `String` перед созданием короткого inline `Scalar`.

### R12-F2. P3: Float formatter создаёт временный String для неизменённого текста

Места: `src/render/canonical.rs:136`, `:198`, `:408`, `:417`, `:429`;
дополнительные callers: `src/parser/classify.rs:121`,
`src/parser/inline.rs:438`.

`canonical_float` всегда возвращает `String`. Для нуля и обычной
десятичной области он делает только `s.to_string()`, после чего writer
сразу копирует эту строку в готовый output buffer. В `parse_strict`
она нужна лишь для сравнения с исходным литералом. Даже короткие
`0.0`, `-0.0` и `1.5` получают отдельную временную материализацию.
В scientific-ветке создаются два промежуточных `String`: `format!`
и результат `normalise_scientific`.

Для G обычных Float это G временных строк, хотя уже имеются исходный
срез и выходной буфер. Речь о числе аллокаций, не о накоплении `O(G)`
живой памяти: строки обрабатываются последовательно, а длина нормальной
binary64-записи ограничена. Асимптотика остаётся линейной; это локальная
возможность убрать лишнюю работу, не новый квадратичный механизм.

Минимальное улучшение: возвращать `Cow<'_, str>` с `Borrowed` для
неизменённой формы; scientific-ветку можно пока оставить owned.
Для writer альтернативой является helper, дописывающий в существующий
буфер, но strict-пути тоже нужно учесть. При изменении сохранить точные
границы `1e-2`/`1e7`, знак нуля, shortest-roundtrip и канонический
payload `LossyScalar`. В этом раунде проверены 13 случаев `f64`, включая
пороговые и крайние значения, с exact canonical bytes, строгим разбором
и проверкой битов. Расхождение R12-F1 учитывается отдельно.

Это анализ явных материализаций по коду, не результат allocation
profiler или замер ускорения. Проценты выигрыша не заявляются. Замечание
не относится к уже устранённому multiline `Vec` из R10-F2 и не отменяет
его исправления.

### R12-F3. P3: rustdoc учит устаревшей грамматике

Места: `src/lib.rs:4`, `:11`.

В crate-level документации сказано, что документ всегда является
неявным Object, а строка `# comment` показана как комментарий. В spec
0.7.0 §3.4 комментарием является только строка с ведущим `##`; один
`#` есть обычное содержимое. По §5.0.1 root может быть Object или Array.

Проверено через публичный `parse` в debug/release:

```ktav
# comment
key: value
```

Результат есть Array из строк `"# comment"` и `"key: value"`, а не
Object с одним ключом. При замене первой строки на `## comment`
получается ожидаемый Object `{"key": "value"}`. Parser ведёт себя
правильно; ошибка находится в публичной документации crate.

Исправление: синхронизировать вводный rustdoc и таблицу Syntax с
актуальной spec, явно описав root-kind detection и `##`. Закрепить
ключевые примеры обычными integration-тестами: текущий блок имеет
тип `text`, а doctests у crate отключены. Это прежний документационный
долг, не причина менять parser или версию проекта.

## Закрытие Раунда 11

**R11-F1 закрыт.** Непустой остаток после `EofAfterWsSkip` возвращается
как последний сырой сегмент. Separator проверяется caller до key
validation, поэтому quote-free потомок больше не меняет категорию из-за
кавычек наверху. Старые unit/integration-оракулы исправлены; новая
матрица покрывает четыре API, кавычки в ключе предка, соседнем value
и array item, SPACE/TAB/U+2000 и разные виды кавычек.

Прежний внешний набор из 26 коротких parser-входов повторно выполнен
против текущей библиотеки в debug/release. Отсутствующий separator
даёт `MalformedInlineCompound`, настоящий `b.: 1` остаётся `EmptyKey`,
допустимый trailing comma принимается. Новые нормативные fixtures
`dotted_key_eof_quote_in_*` в рабочем spec тоже прошли. Текстовое
обоснование root quote-флага исправлено в коде и отчёте R10-F1.

Повторных quote-prescan по глубине не добавлено. Повторно выполненный
`ix_probe_r10f1_quote_prescan_counters` дал те же 14 строк P/E counters,
что в раунде 11: при M=512 и D=1/4/8/32/64 объём проверок равен
1039/1075/1123/1411/1795 байтам; при D=8 и M=8192/65536 равен
16483/131171. Для этой семьи остаётся `2*M + 12*D + 3`, а не множитель
`M*D`. Это объём диапазонов prescan, не общее время parser.

Известный `O(C log C)` компонент сортировки/поиска C сохранённых inline-границ
остаётся; оснований менять выбранный sorted `Vec` без нового профиля
не получено. Ранее отмеченный резерв arena по размеру исходного текста
также остаётся профильным кандидатом, не новой находкой этого раунда.
Multiline emitter по-прежнему обходится без промежуточного `Vec`;
шесть дополнительных multiline roundtrip/idempotence случаев прошли.
