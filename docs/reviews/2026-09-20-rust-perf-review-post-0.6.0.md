# Перф-ревью изменений после 0.6.0

Дата: 2026-09-20. Предмет: всё, что приехало в крейт `ktav` после
0.6.0 — 0.6.x, 0.7.0, 0.7.1 и неизданная 0.8.0. Вопрос, на который
отвечает документ: есть ли места, которые можно ускорить сильно, а не
на уровне шума.

Метод: чтение горячих путей плюс уже снятые числа из
`bench-baseline.md` (прогон 2026-09-19). **Бенчмарки в рамках этого
ревью не запускались** — это ощутимая нагрузка на машину, и она
требует отдельного решения. Поэтому находки разделены на три группы:
доказуемые чтением, измеренные но не атрибутированные, и проверенные
и оправданные.

---

## 1. Находки, доказуемые чтением кода

### P1. `emit_canonical` и `render` обходят дерево трижды и дублируют работу по каждому скаляру

`src/render/canonical/walk.rs:20-21` и `src/render/render.rs:29-36`
начинаются одинаково:

```rust
super::representable::check_representable(value)?;
let mut out = String::with_capacity(estimate_size(value));
```

Это два полных рекурсивных обхода дерева до того, как записан первый
байт, и третий — собственно эмиссия. Хуже, что первый и третий обходы
делают по каждому узлу пересекающуюся работу:

| Узел | `check_representable` | эмиттер |
|---|---|---|
| `Float(s)` | `s.parse::<f64>()` ради `is_nan()/is_infinite()` (`representable.rs:54`) | `canonical_float(s)` снова делает `s.parse()` (`canonical/num.rs:19`) |
| `String(s)` | `s.contains('\r')` + `string_needs_multiline(s)` (`representable.rs:66-69`) | ровно те же два вызова (`pair.rs:47-50`) |
| `String(s)` многострочная | `choose_multiline_form(s, false)` — полный построчный скан (`representable.rs:76`) | `choose_multiline_form(s, true)` — тот же скан ещё раз (`pair.rs:57`) |

То есть на каждый Float приходится **два** `strtod`, на каждую строку —
**два** полных скана, на каждую многострочную строку — **два**
построчных прохода, и сверх этого один лишний полный обход дерева под
`estimate_size`.

Почему пре-пасс вообще есть: § 5.9.0 требует «нет частичного вывода при
отказе», а ошибка должна нести путь ключей (`Error::UnrepresentableAt`).

Как убрать, не теряя контракт: эмиттер уже пишет в **локальный**
`String`, который возвращается только при `Ok`. Значит частичного
вывода не бывает по построению, и пре-пасс нужен не для этого, а только
чтобы собрать путь ключей. Отсюда схема: эмитить сразу, а при
`Err(Unrepresentable)` — один раз прогнать `check_representable`, чтобы
получить путь и вернуть `UnrepresentableAt`. Горячий путь перестаёт
платить за холодный.

Ожидаемый эффект: минус один-два полных обхода дерева, минус один
`strtod` на Float, минус один-два скана на String. Величина зависит от
доли строк и float-ов; точную цифру даст бенч.

Риск: средний. Нужно, чтобы эмиттер выдавал те же семь `ReasonCode` и
чтобы сохранился фиксированный порядок § 5.9.0 (корень проверяется до
узлов). Ловится корпусом: 223 `valid/`, 5 `unrepresentable/`, 4
`parseable-unrepresentable/`.

### P2. `to_string_force_strings` копирует всё дерево целиком

`src/render/render.rs:88-110`: `coerce_scalars_to_strings` строит новый
`Value` — клонирует каждый ключ и каждый скаляр, аллоцирует новый
`ObjectMap` на каждый объект — и только потом зовёт `render`. Пиковая
память ×2 плюс полный обход с аллокациями, ради того что сводится к
одному булеву флагу в эмиттере.

Ожидаемый эффект: убирает обход и всю его аллокацию. Риск: низкий,
поведение задаётся флагом, тесты `force_strings` уже есть.

### P3. `matches_integer_grammar` делает работу дважды и выбрасывает результат

`src/parser/syntax/classify.rs:587-593`:

```rust
pub fn matches_integer_grammar(s: &str) -> bool {
    if try_parse_integer(s).is_some() { return true; }
    matches_integer_grammar_syntax(s)
}
```

`try_parse_integer` — это полноценный разбор с `checked_mul`/
`checked_add` и обработкой знака и переполнения; его значение здесь
немедленно выбрасывается. При этом `matches_integer_grammar_syntax` —
надмножество: он принимает и то, что переполняет i64. Любая строка, на
которой парсер вернул `Some`, синтаксически совпадает и так.

Функция зовётся из `needs_raw_marker` (`render/helpers.rs:408`), то есть
на **каждый String-скаляр во всех трёх писателях**: `render`,
`emit_canonical` и потоковый serde-сериализатор.

Ожидаемый эффект: один проход вместо двух на числовых строках, минус вся
арифметика. На нечисловых строках обе ветки отказывают за O(1), там
выигрыш околонулевой.

Риск: низкий, но требует доказательства: `parse_decimal_int` против
`check_decimal_digits` и `parse_prefixed_int` против
`check_prefixed_digits` должны совпадать по правилам подчёркиваний и
префиксов. Это зеркальные реализации, но эквивалентность стоит закрепить
property-тестом, а не глазами.

### P4. Каждый ключ сканируется дважды

`render/helpers.rs:88-117` (`key_segment_needs_quotes`) делает полный
`key.bytes().any(...)` по структурным байтам. Затем
`render/helpers.rs:132-139` (`push_bare_key`) делает ещё один полный
`key.bytes().any(...)` по пересекающемуся, более широкому предикату.
Оба — часть § 5.9.10, приехавшего в 0.7.0 (`c8ceab9`).

Сливается в один проход, который сразу определяет форму и пишет.
Дополнительно просится быстрый путь «весь ключ — ASCII буквы/цифры/
`-`/`_`» → `push_str` без разбора; в конфигах это подавляющее
большинство ключей.

Ожидаемый эффект: минус один полный скан на каждый ключ документа.
Риск: низкий, писательские фикстуры `key_escaping`/`quoted_keys`
проверяют вывод байт-в-байт.

### P5. Потоковый сериализатор стартует с фиксированных 2 КБ

`src/ser/text_serializer/root.rs:21`: `String::with_capacity(2048)`.
Для `large` из `vs_json` (1000 upstream-ов, сотни килобайт вывода) это
7–8 реаллокаций, каждая с `memcpy` всего накопленного буфера.

Дёшево улучшить, не зная размер заранее: начинать меньше для крошечных
документов и расти агрессивнее, либо дать публичный
`to_string_with_capacity` для вызывающих, которые размер знают.

### P6. Мелкие аллокации на путях экранирования и научной записи

- `render/helpers.rs:41-43`: `push_unicode_escape` делает
  `format!("\\u{:04X}")` — аллокация `String` на каждый экранируемый
  код-поинт. Заменяется записью четырёх байт в `out` напрямую.
- `render/canonical/num.rs:34,65`: `canonical_float` в научной области
  делает `format!("{:e}")`, затем `normalise_scientific` — ещё один
  `format!`. Две аллокации на каждый float вне `[1e-2, 1e7)`.

Оба — холодные на типичных конфигах, но бесплатны в починке.

## 2. Измерено, но не атрибутировано

Из `bench-baseline.md` (прогон 2026-09-19):

**`render/` — ktav против serde_json.** Было «ktav на 25 % быстрее»
на `small`; стало «json в 2.6× быстрее» на `small`, 3.1× на `medium`,
2.7× на `large`. Движение односторонее на всех трёх размерах, то есть
по собственному правилу этого документа — сигнал, а не шум.

Существенная поправка к формулировке в `bench-baseline.md`: этот ряд
зовёт `ktav::to_string(&cfg)` на типизированной структуре
(`benches/vs_json.rs:150`), то есть меряет **потоковый serde-
сериализатор**, а не `render(&Value)`. Значит гипотеза про «`render`
теперь обслуживает и форматтер» к этому ряду не относится, и P1 его не
сдвинет. Для него релевантны P3, P4, P5 — плюс структурная разница,
которую нельзя убрать: ktav пишет отступы и перевод строки на пару, а
`serde_json::to_string` пишет компактно, так что и байт на выходе
больше.

**`parse_to_value/large`**: преимущество ktav сжалось с 1.7× до 1.05×.
Причина не установлена.

**`format_str`**: 2–4× от обычного `parse` на тех же размерах,
пропускная способность ровная (~21–26 МиБ/с), то есть размерного обрыва
нет. Потолок не исследован — у пути нулевая история измерений, он новый.

Чтобы атрибутировать любую из трёх строк, нужен профиль или точечные
микро-бенчи. Это отдельная нагрузка и отдельное решение.

## 3. Проверено и оправдано — сюда не копать

Чтобы не тратить на это время повторно:

- **`src/whitespace.rs`** — ASCII-путь идёт первым, оба предиката
  `#[inline]`, аллокаций нет, `leading_whitespace_run` декодирует `char`
  только при реальном не-ASCII ведущем байте. Замена делегирования
  `char::is_whitespace` на замкнутый список § 3.3 (`deee0e2`) стоила
  дёшево.
- **Представление данных** — `ObjectMap` это `IndexMap` с `FxHash`,
  `Scalar` это `CompactString`: короткие ключи конфигов живут инлайн, без
  кучи. Гипотеза `bench-baseline.md` про «бухгалтерию IndexMap» слабая.
- **Горячий цикл владеющего парсера** — на строку не аллоцирует;
  единственные `to_string()` в `syntax/collecting.rs` относятся к сбору
  многострочных тел, где аллокация неизбежна.
- **`is_float_literal`** — уже имеет ранний отказ по первому байту плюс
  `memchr3` на `.`/`e`/`E`.
- **`has_redundant_leading_zero`** (новое в 0.8.0) — два сравнения
  байтов с ранним выходом, на профиль не влияет.

## 4. Рекомендация

Порядок, если браться:

1. **P3 и P4** — дёшево, низкий риск, бьют ровно по тому пути, где
   измерен односторонний регресс (`ktav::to_string`). Делать первыми и
   сразу померить `vs_json/render`: это проверит и находки, и гипотезу
   об их вкладе.
2. **P1** — самая крупная структурная находка, но она про
   `render`/`emit_canonical`, то есть про C ABI и корпус, а не про ряд
   `vs_json/render`. Отдельная задача, средний риск, нужен аккуратный
   перенос `ReasonCode` в эмиттер.
3. **P2, P5, P6** — мелочь, можно попутно.

Честный ответ на исходный вопрос «можно ли сильно ускорить»: по
`emit_canonical`/`render` — да, там доказуемо лишний полный обход дерева
и двойной `strtod`/двойной скан на скаляр. По ряду `vs_json/render`,
где измерен самый заметный разрыв, — пока неизвестно: находки P3–P5
реальны, но что именно даёт разрыв в 3×, чтением не доказывается.
Нужен профиль.

## 5. Что реализовано

Сделано в том же проходе. Правки поведения нет: полный набор тестов,
`cargo fmt --check` и `cargo clippy --all-targets` зелёные, включая
корпус 0.8 (223/74/5/4/13) и цикл в `tests/error_envelope/shape.rs`,
который проверяет все семь `ReasonCode` с точными путями ключей.

**P1 — пре-пасс убран с горячего пути всех трёх писателей.**
`check_representable` больше не вызывается перед эмиссией. Ключевое
наблюдение: гарантию § 5.9.0 «нет частичного вывода при отказе» давал не
пре-пасс, а то, что каждый писатель собирает документ в ЛОКАЛЬНОМ
`String` и отдаёт его только при `Ok`. Пре-пасс покупал лишь путь
ключей, а он нужен только после того, как отказ уже случился. Теперь
условия § 5.9.0 ловятся по месту эмиссии (`empty_key_error`,
`reject_non_finite` / `canonical_float_checked`, `cr_error`, три кода из
`choose_multiline_form`), а `representable::attach_path` достраивает
путь на холодном пути. Фиксированный порядок § 5.9.0 сохранён: корневое
условие решается до захода в узлы, эмиттеры идут в порядке документа.

Следствия: на Float — один `parse::<f64>()` вместо двух; на String —
один скан вместо двух, на многострочной — один построчный проход вместо
двух; обходов дерева два вместо трёх. **`estimate_size` намеренно
оставлен** — он пресайзит буфер и не делает побайтовой работы, так что
второй обход тут дешевле реаллокаций, которые он предотвращает.

**P1b (найдено уже в ходе правки) — форматтер строил целое дерево ради
проверки.** `emit_formatted` вызывал
`check_representable(&to_plain_value(&doc.root))`, то есть
материализовывал полный throw-away `Value` из trivia-дерева — новый
`ObjectMap` на каждый объект, клон каждого ключа и скаляра — только чтобы
общий предикат получил аргумент нужного типа. Теперь `to_plain_value`
вызывается лишь на холодном пути отказа. Это прямо на пути `format_str`,
который и мерился в 2–4× от обычного парса.

**P2 — `to_string_force_strings` больше не копирует дерево.**
`coerce_scalars_to_strings` удалён; вместо него флаг `force_strings`
протянут в `render_document` / `render_object_body` / `render_pair` /
`render_array_item`, а листовые скаляры уходят в строковый эмиттер через
`forced_string_text`. Документированная асимметрия сохранена:
`NonFiniteFloat` здесь не срабатывает, потому что Float становится
String до проверки. Это единственный контракт, который флаг мог сломать
молча, и его ничто не закрепляло — добавлен
`non_finite_float_is_coerced_instead_of_rejected`, проверяющий обе
половины (`render` отвергает, `to_string_force_strings` принимает).

**P3 — `matches_integer_grammar` больше не зовёт `try_parse_integer`.**
Импликация «разбор удался ⇒ синтаксис совпал» доказана по построению
(`parse_*_int` возвращает `Some` только когда первый байт — цифра, а
каждый следующий — цифра или одиночное неконцевое `_`, то есть ровно
условие `check_*_digits`) и закреплена тестом
`parse_success_implies_grammar_match` на границах: все префиксы основ,
раскладки подчёркиваний, знаки, пределы i64 и переполняющие значения.

**P4 — ключ сканируется один раз.** `key_segment_needs_quotes` и
`push_bare_key` слиты в один проход внутри `push_escaped_key_segment`:
структурный байт завершает скан и уводит в кавычки, остальное из
escape-набора лишь помечает, что тело надо переписать, а ключ без того и
другого пишется как есть.

**P6 — аллокации на путях экранирования убраны.**
`push_unicode_escape` пишет четыре hex-байта прямо в буфер (с откатом на
`format!` для не-BMP, чего сегодня не бывает); `normalise_scientific`
собирает результат одним `push_str` с точной ёмкостью.

Заодно устранена латентная паника: `normalise_scientific` делал
`&raw[e_pos + 1..]` от `unwrap_or(raw.len())`, то есть падал на входе без
`e`. Единственный такой вход — нефинитный Float (`{:e}` даёт `NaN`), и
раньше до него не доходило только потому, что пре-пасс отвергал NaN
раньше. Ровно этот порядок P1 и менял, поэтому теперь нефинитность
отвергается внутри `canonical_float_inner`, а срез защищён `let Some(…)
else`.

**P5 не делался.** Фиксированные 2048 байт в
`ser::text_serializer::root` — это подгонка без замера: при удвоении
роста для 500 КБ вывода набегает порядка 1 МБ `memcpy`, то есть единицы
процентов, а выбрать лучшее стартовое значение, не зная размера
документа, нельзя. Принципиальное решение — потоковый `to_writer` вместо
сборки в `String`, то есть новый публичный API, а не оптимизация. Оставил
как есть.
