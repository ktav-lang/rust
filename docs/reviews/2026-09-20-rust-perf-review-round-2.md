## Метод

`valgrind --tool=callgrind` в WSL2 (Ubuntu 24.04) поверх
`examples/callgrind_writers.rs`, сбор включается только внутри
`measured_loop` (`--collect-atstart=no --toggle-collect='*measured_loop*'`),
поэтому построение фикстуры в профиль не попадает и вычитать его не нужно.
Атрибуция по функциям — `callgrind_annotate`. Все числа ниже —
**инструкции**, `medium_50k`, 20 итераций.

Инструкции — не циклы: callgrind не моделирует ни предсказатель переходов,
ни промахи кэша. Для «где именно тратится» этого достаточно, для «во
сколько раз станет быстрее» — нет.

Итоги по workload (для контекста, не для сравнения между собой —

**N1. Одна таблица классов байт вместо цепочек сравнений, и один проход
по строке вместо трёх-четырёх.** Самая крупная находка раунда.

Сейчас значение-строка в паре получает до четырёх независимых проходов:
`s.contains('\r')` (это и есть `memchr_aligned`, 4.73 %),
`string_needs_multiline` (18.76 %), затем `needs_raw_marker` →
`matches_integer_grammar` + `is_float_literal` (1.76 % + 2.55 %). Каждый
проход отвечает на свой вопрос об одних и тех же байтах.

`push_escaped_key_segment` внутри цикла ветвится девятерным `match` по
структурным байтам плюс проверки control-байт — на короткий ASCII-ключ
это уже неплохо после фьюза из первого раунда, но всё ещё цепочка
сравнений на байт.

Предложение из двух частей:
- **256-байтная таблица классов** (битовые флаги: STRUCTURAL / NEEDS_ESCAPE
  / CTRL / QUOTE_LEAD) — одна загрузка и один тест на байт вместо цепочки.
  Бьёт по `push_escaped_key_segment` во всех трёх писателях сразу.
- **Слитный предикат для значения-строки**, возвращающий за один проход
  сразу: есть ли CR, есть ли control-байт кроме TAB, является ли первый
  или последний код-поинт § 3.3-пробелом, и префильтр «похоже ли на
  число» (первый байт — цифра/знак). Последний отсекает
  `matches_integer_grammar`/`is_float_literal` для подавляющего
  большинства строк до входа в них.

Потенциал: под ударом 40.4 % `emit_canonical` и 34.8 % `to_string`.
Реалистично снять примерно половину этого — но это оценка, а не
измерение; проверяется тем же harness'ом.

Риск: средний-высокий. Эти функции решают байт-в-байт вывод; сеть —
223 `valid/` фикстуры с каноническими оракулами плюс писательские
фикстуры `key_escaping`/`quoted_keys`.

## 2. Исправление к первому раунду: `estimate_size` надо убрать

В прошлом отчёте я написал, что оставил `estimate_size` намеренно, потому
что «он пресайзит буфер и не делает побайтовой работы, так что второй
обход дешевле реаллокаций, которые он предотвращает». **Это неверно, и
теперь это измерено.**

`emit_canonical/medium_50k`, n=20:

| Вариант | Инструкции | Δ |
|---|---|---|
| `String::with_capacity(estimate_size(value))` | 25 002 906 | — |
| `String::new()` | 23 022 549 | **−7.9 %** |

И главное — стоимость никуда не переехала: `__memcpy_avx_unaligned_erms`
составил **1 037 320 инструкций в обоих** прогонах, `__memset` —
418 880 в обоих. Байт в байт. То есть отказ от пресайза не добавил ни
одного копирования: `String` растёт удвоением, а glibc для крупных блоков
расширяет их через `mremap` вместо копирования, так что предотвращать
было нечего.

Сам `estimate_size` стоит 2 045 780 инструкций (8.18 %), а общая разница
1 980 357 — то есть путь роста буфера обошёлся примерно в 65 тысяч
инструкций, в тридцать раз дешевле обхода, который его «экономил».

Оговорка, которую надо снять перед правкой: измерение сделано под glibc в
WSL. Аллокатор Windows ведёт себя иначе, и инструкции не считают
page fault'ы от повторного роста. Правку стоит сделать и перемерить на
обеих платформах, а не принимать на веру — но направление теперь
известно, и оно противоположно тому, что я написал в прошлый раз.

То же касается копии `estimate_size` в `render.rs`.

## 3. Парсинг: ключ обрабатывается четырьмя отдельными проходами

`parse/medium_50k`:

| Функция | Доля |
|---|---|
| `Parser::handle_line` | 7.00 % |
| `build::validate::check_key` | 6.04 % |
| `inline::keys::scan_unescaped_colon` | 5.81 % |
| `inline::keys::key_is_single_segment` | 4.90 % |
| `memchr::avx2::Two::find_raw` | 4.76 % |
| `memcpy` (libc) | 4.58 % |
| `<str>::trim_matches::<is_ktav_whitespace>` | 4.45 % |
| `core::slice::memchr::memchr_aligned` | 3.63 % |
| `build::insert::insert_value` | 3.25 % |
| `_int_malloc` (libc) | 3.05 % |
| `classify::classify_value_start` | 3.03 % |
| `inline::keys::decode_key_segment` | 2.82 % |
| `indexmap::Entry::new` | 2.82 % |
| `ryu::pretty::format64` | 2.71 % |

**N3.** `scan_unescaped_colon` + `key_is_single_segment` + `check_key` +
`decode_key_segment` = **19.57 %**, и это четыре прохода по одному и тому
же тексту ключа: найти разделитель, выяснить, односегментный ли он,
провалидировать, декодировать. Скан разделителя уже идёт побайтово — он
может в том же проходе запомнить, встречались ли `.` и `\`, что бесплатно
отвечает на вопрос `key_is_single_segment` и говорит
`decode_key_segment`, нужно ли вообще что-то делать. Ожидаемо снимает
большую часть 4.90 % и заметную долю 2.82 %.

**N4.** `trim_matches::<is_ktav_whitespace>` — **4.45 %**. Это
код-поинтовый трим: `str::trim_matches` декодирует `char` на каждом шаге,
хотя в `whitespace.rs` уже есть байтовый быстрый путь
(`inline_whitespace_ascii`), которым пользуется
`leading_whitespace_run`. Нужен `trim_ktav_whitespace(&str) -> &str`,
идущий по байтам и декодирующий `char` только при реальном не-ASCII
ведущем байте, и перевод горячих тримов парсера на него. Риск низкий:
семантика § 3.3 не меняется, инвариант уже закреплён тестом
`ascii_byte_fast_path_matches_the_inline_view`.

**N5.** `_int_malloc` 3.05 % + `indexmap::Entry::new` 2.82 % +
`memcpy` 4.58 % — построение дерева. Корневой `ObjectMap` создаётся
пустым и растёт; оценка числа пар по количеству строк документа дала бы
пресайз. В отличие от N2 это пресайз *хеш-таблицы*, а не строкового
буфера: там рост означает rehash, а не `mremap`, так что механизм
экономии другой и проверять надо отдельно.

## 4. Что в профиле есть, но трогать не стоит

- `ryu::pretty::format64` 2.71 % при парсинге — каноникализация float'ов,
  неизбежна по § 5.2 r14 / § 5.9.8.
- `memchr::avx2::Two::find_raw` 4.76 % — уже SIMD, это правильный
  инструмент на своём месте.
- `dec2flt::parse::parse_number` 2.30 % в `emit_canonical` — единственный
  оставшийся разбор float'а на вызов (второй убран в первом раунде).
- `format_str` (133 M) против `parse` (101 M): накладные расходы
  форматтера над обычным парсингом — примерно 32 M, из которых
  `PositionedParser::handle_line` 8.5 M и `insert_value::<PObject>` +
  `PObject::insert_leaf` 6.4 M. Это цена trivia-дерева, то есть цена
  самой фичи, а не потеря.

## 5. Порядок

1. **N2** — измерено, направление известно, правка в одну строку на
   писателя. Сделать первым, перемерить на Windows.
2. **N1** — самая крупная (40 % `emit_canonical`, 35 % `to_string`), но и
   самая рискованная. Таблицу классов и слитный предикат стоит делать
   двумя отдельными шагами с прогоном корпуса после каждого.
3. **N4** — дёшево, низкий риск, 4.45 % парсинга.
4. **N3** — 19.6 % парсинга, но требует аккуратности вокруг § 4 и § 5.3.3
   (квотированные сегменты, экранированный `:`).
5. **N5** — проверить гипотезу измерением прежде, чем писать код.

Всё воспроизводится: `examples/callgrind_writers.rs`, команды — в его
шапке.
