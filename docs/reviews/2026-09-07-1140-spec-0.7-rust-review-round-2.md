## Вердикт

**NO-GO: два P1 и два P2.** Штатные conformance, debug/release tests,
форматирование и Clippy проходят. Исходные репродьюсеры предыдущего ревью
закрыты, но новая реализация dotted-key merge содержит panic и допускает

проверку пустого имени ключа. Conformance-runner не проверяет результат
`from_str()`, поэтому эти дефекты не влияют на его зелёный статус.

## Findings

### R2-F1. P1: merge-проход не учитывает compound-элементы массивов

Места: `src/thin/merge.rs:90`, `:154-162`, `:202`;
вызов merge из `src/lib.rs:147`.

Короткий валидный документ:

```ktav
a.x: 1
items: [[2]]
a.y: 3
```

`parse()` возвращает Object с `a = {x: 1, y: 3}` и `items = [[2]]`.
`from_str::<serde_json::Value>()` паникует:

```text
src/thin/merge.rs:202:
stream is balanced; root frame always open
```

Воспроизведено в debug и release. Замена `[[2]]` на `[{b: 2}]` даёт тот же
panic. Если повторно открываемый объект находится внутри root Array,
воспроизведена ошибка `expected Key or EndObject in map, got Some(EndArray)`.

Причина: `merge_reopened()` создаёт stack frame для root opener и для
`Key + BeginObject/BeginArray`. Открывающий event compound-элемента массива
попадает в общий `ev =>` и не создаёт frame. Закрывающий event при этом
безусловно выполняет `stack.pop()`. Состояние стека и выходная структура
разрушаются. Merge включается при любом reopen в документе, поэтому
поломка массива может находиться в другой ветви относительно dotted keys.

Исправление: учитывать каждый compound opener/closer, включая безымянные
элементы массива, с отдельным дочерним buffer. Проверить обе комбинации
Object-in-Array и Array-in-Array вместе с reopen в той же и другой ветви.
Panic нельзя заменять на пропуск events: требуется сохранить точную структуру.

### R2-F2. P1: дочерние пути explicit Object не участвуют в проверке последующего dotted re-entry

Места: `src/thin/event_parser.rs:219` (`Frame::new_object`),
`:851-885` (поиск prefix), `:1015-1065` (`register_value_path`),
`:1127-1143` (закрытие frame); `src/thin/merge.rs:139-144`.

Некорректный документ:

```ktav
a: {x: 1}
a.x: 2
```

Owned `parse()` правильно возвращает `DuplicateKey` для `a.x`.
`parse_events()` возвращает `Ok(())`, а
`from_str::<serde_json::Value>()` успешно возвращает `{"a":{"x":2}}`:
первое значение молча потеряно.

То же воспроизведено с explicit Object в многострочной форме:

```ktav
a: {
    x: 1
}
a.x: 2
```

Дополнительный отрицательный пример `a: {x: 1}\na.x.y: 2\n` также
принимается `parse_events()`, хотя спуск через scalar должен быть
`KeyPathConflict`.

Причина: родительская таблица `paths` регистрирует только Object по пути
`a`. Внутреннее `x` хранится в собственном frame либо уже разобранном inline
Value; эти дочерние пути не переносятся в родительскую таблицу. Последующая
регистрация `a.x` видит отсутствующий путь. Merge-проход предполагает, что
проверка конфликтов уже выполнена, и оставляет повторные scalar keys;
обычный map-десериализатор применяет last-write-wins.

Исправление: единая информация о занятых дочерних путях для explicit,
inline и synthetic Objects. Проверять повторный key и спуск через scalar
до выдачи успешного `parse_events()` и до merge. Нужны отрицательные
комбинационные тесты, а не только допустимое добавление нового соседнего ключа.

### R2-F3. P2: root tuple variant обходит EmptyKeyName

Место: `src/ser/text_serializer.rs:320-341`,
`RootSer::serialize_tuple_variant()`.

Воспроизводитель на штатном Serde derive:

```rust
#[derive(serde::Serialize)]
enum E {
    #[serde(rename = "")]
    Empty(i64, i64),
}
let value = E::Empty(1, 2);
```

`to_string(&value)` возвращает `Ok(": [\n    1\n    2\n]\n")`.
`ser::to_value(&value)` с последующим `render()` правильно возвращает
`Unrepresentable(EmptyKeyName)`. Это две поверхности одного и того же
программного Value; пустой ключ должен быть отвергнут по §5.9.0.

Новая root tuple-ветвь напрямую вызывает `push_escaped_key_segment` и не
проверяет `variant.is_empty()`. Выход не представляет исходный Object.

Исправление: вернуть `Error::Unrepresentable(ReasonCode::EmptyKeyName)` до
вывода key. Покрыть пустую и непустую tuple variant, обе writer-поверхности
и отсутствие успешного результата с повреждённой структурой.

### R2-F4. P2: thin conformance проверяет принятие, но не результат from_str

Места: `tests/spec_conformance.rs:733-787`, особенно `:765`;
`src/thin/mod.rs` (`parse_events` и `parse_events_merged`).

Новый `valid_fixtures_parse_via_thin_api()` вызывает
`parse_events(&text, |_| {})` и проверяет только отсутствие ошибки.
Он не собирает Value из событий, не сравнивает JSON-оракул и не вызывает
`from_str()`. Публичный `parse_events()` выдаёт raw events, тогда как
`from_str()` использует дополнительный `merge_reopened()` при reopen.
Следовательно, текущий успешный thin-conformance не исполняет merge,
который вызывает panic в R2-F1.

Прежнее исправление числового comparator полезно, но не распространяется
на проверку thin-result: comparator используется в owned-проверках.

Исправление: прогонять corpus также через конечный Serde-путь с
типосохраняющим visitor/oracle и сравнивать полный результат, включая
порядок, числовой kind и знак нуля. Добавить комбинированные fixtures для
новых R2-F1/R2-F2. При адаптации тестов учитывать `serde_json` с
`arbitrary_precision`: прямое сравнение только текстовых Float-форм и
использование его приватного Number envelope не заменяют Ktav Value oracle.

## Качество и улучшения

В `src/thin/merge.rs:21` заявлена сложность O(n), но `find_seen()`
(`:206-208`) линейно ищет ключ в `seen: BumpVec`. Для k различных
object-valued keys внутри одного buffer требуется до k(k-1)/2 сравнений.
Merge активируется даже при одном повторном открытии в документе.
Аналогично `paths.iter().find()` в `event_parser.rs:1024` линейно проверяет
все уже зарегистрированные пути для каждой новой пары.

Это статический вывод об алгоритме; нагрузочные тесты и бенчмарки не
запускались. Рекомендуется индекс по декодированным сегментам либо дерево
путей с сохранением порядка вставки. Сначала исправить R2-F1/R2-F2, затем
измерить обычные wide-object/dotted-key workloads. Не добавлять stress-тесты,
которые лишь нагружают машину и не проверяют конкретный инвариант.

Root Array serialization использует `Rc<Cell<bool>>` для локального решения
о внешних скобках. Это не дефект корректности; после исправления обязательных
ветвей можно рассмотреть более простой способ передавать решение без
дополнительной heap allocation, если измерения оправдают изменение.

Общий приоритет: обеспечить одинаковую валидацию и результат всех parser
поверхностей. Сейчас patch для принятия ранее запрещённых документов
исправил положительные примеры, но не полностью сохранил отрицательные
инварианты и структуру events.

## Область и ограничения

Ревью охватывает net delta `5177eac..6c29d80`, новые parser/merge/serializer
пути и conformance-runner, соответствующие правила подключённой spec 0.7,
а также повторные локальные debug/release/lint проверки. Это не утверждение
о полном аудите зависимостей, всех возможных входов и всех target-платформ.
MSRV 1.71, Miri, supply-chain audit, Linux/macOS и remote CI в этом раунде
не запускались. Производительность оценена статически, без benchmark claims.

Версия crate и `spec-version` в metadata намеренно остаются `0.6.4`, как
объясняет README для подготовки draft 0.7. Это не отмечено как дефект и
не изменялось в ревью.

отчёт. Исправления реализации и push не выполнялись.
