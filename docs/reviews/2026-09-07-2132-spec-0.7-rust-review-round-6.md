## Найденные Проблемы

Пять основных находок: одна P1 и четыре P2. Среди них одна ошибка
соответствия spec, три проблемы асимптотики и невалидные данные бенчмарков.
Это находки на
текущем состоянии дерева, не утверждение, что все они внесены последними
пятью коммитами. Остаток P3 из раунда 5 описан отдельно в таблице закрытия.

Для R6-F1 выполнены воспроизводители на обоих публичных parser API в
debug/release. Для R6-F2--R6-F4 приведены статические доказательства
сложности, а не результаты нагрузочных измерений. Для R6-F5 проверен
один небольшой образец существующего генератора без запуска Criterion.

Используемая шкала:

- **P0:** немедленный безусловный блокер, требующий экстренного исправления. Не найден.
- **P1:** серьёзный риск, который следует устранять в ближайшую очередь. R6-F3 отнесён сюда по доказанному механизму роста памяти, без запуска OOM-нагрузки.
- **P2:** подтверждённый дефект для планового исправления; не косметическое замечание.
- **P3:** менее срочное требование или возможность улучшения, для которой допустима отдельная проверка пользы.

Итого с кандидатами на оптимизацию и перенесённым замечанием:
**P0: 0; P1: 1; P2: 4; P3: 4.** Приоритет риска и способ подтверждения
различаются: P1 здесь основан на анализе алгоритма, а не наблюдённом падении.

### R6-F1. P2: вложенный Object отвергается из-за ложного quoted key внутри Array

Место: `src/parser/inline.rs:1285`, `:1263` и `:238`.

Валидный документ:

```ktav
[{a: [1, "x], "b}c": 2}]
```

Ожидаемый результат в JSON-нотации:

```json
[{"a": [1, "\"x"], "b}c": 2}]
```

Кавычка в элементе Array является обычным символом, не началом quoted
scalar: по разделу 5.3.3 quoting существует только у key segments.
Разделы 5.8.3 и 5.8.4 разрешают эти элементы и вложенный Object.

`parse()` и `from_str::<serde_json::Value>()` вместо результата возвращают
`MalformedInlineCompound`: якобы после matching closer осталось содержимое.
При этом тот же Object без внешнего Array успешно разбирается:

```ktav
{a: [1, "x], "b}c": 2}
```

Обёртка `{outer: {a: [1, "x], "b}c": 2}}` также ломается. Вариант с
одинарной кавычкой `[{a: [1, 'x], 'b}c': 2}]` воспроизводит тот же отказ.

Причина: `scan_inline_closer()` уже учитывает тип текущего scope, но
`find_matching_close()` в Object-ветви всё ещё включает `in_key/seg_start`
на любой запятой, включая запятую вложенного Array. `"x` ошибочно
считается началом quoted key; открывающая кавычка настоящего ключа
`"b}c"` закрывает этот ложный span. После этого `}` внутри настоящего
ключа преждевременно завершает Object.

Вложенный `parse_inline_value_raw()` доверяет полученному `Some(close)`;
правильный scanner вызывается только при `None`. Поэтому исправление
категорий из R5-F4 корректно классифицирует неверно найденную границу,
но не исправляет саму границу.

Исправление: использовать единую модель scope/key/value при поиске границ
во всех путях, а не оставлять старый scanner нормативным источником для
вложенных значений. Нужны проверки оборачивания валидного Object в Array
и в значение другой пары, всех трёх key delimiters и кавычек в Array
scalars. Совпадение owned/thin не защищает от этого общего дефекта.

### R6-F2. P2: таблица путей thin-парсера квадратична даже для плоского Object

Место: `src/thin/event_parser.rs:1071`, `:1117`; дополнительные поиски
префиксов на `:898` и проверки при переносе путей на `:1298`.

Для многострочного Object с `K` различными одно-сегментными ключами
`register_value_path()` перед каждой вставкой линейно просматривает
все ранее зарегистрированные пути. Число проверок записей:

```text
0 + 1 + ... + (K - 1) = K(K - 1)/2
```

Это `Theta(K^2)` проверок путей, плюс стоимость сравнения самих ключей.
Dotted keys, inline compounds и повторные открытия для этого не нужны.
Fast path `reconcile_dotted_key()` на `:821` не устраняет проблему:
после него одно-сегментный путь всё равно регистрируется общим методом.

Owned-парсер использует `ObjectMap::entry()` (`src/parser/insert.rs:54`),
поэтому два публичных пути имеют существенно разную стоимость широкого
Object. Зелёные fixtures малого размера этого не показывают.

Исправление: индексировать идентичность декодированного пути, например
через идентификаторы узлов и индекс `(parent_id, decoded_segment)`.
Для плоского Object целиться в ожидаемое амортизированное `O(K)` число
поисков, для общего случая учитывать число сегментов и байты ключей.
Порядок событий/первого появления хранить отдельно от индекса. Нельзя
заменять сегменты строкой `join(".")`: буквальная точка в quoted или
escaped key не эквивалентна разделителю пути.

### R6-F3. P1: закрытие глубокой цепочки Object копирует кубический объём метаданных

Место: `src/thin/event_parser.rs:1284`, `:1289`, `:1292` и `:1307`.

При закрытии явного многострочного Object все его дочерние пути
переносятся в таблицу родителя с приписанным `base`. Для каждого пути
создаётся временный `Vec<&str>`, затем полная копия в bump arena.
При закрытии следующего предка эти уже перенесённые пути копируются снова.

Достаточно цепочки следующего вида; небольшой вариант проверен обоими API:

```ktav
a: {
a: {
a: {
x: 1
}
}
}
```

Пусть `D` означает число Object-уровней такой цепочки, включая корневой.
В таблицах последовательно закрываемых предков появляются пути длиной
`1..j`. Общее число
выделенных слотов `&str` для всех этих полных путей имеет порядок:

```text
sum(j = 1..D, sum(k = 1..j, k))
    = D(D + 1)(D + 2)/6
    = Theta(D^3)
```

Речь о копировании ссылок, не повторном копировании байтов ключей.
Срезы выделены через `bump.alloc_slice_copy()` и не освобождаются при
закрытии frame: arena живёт до конца `from_str()`. Поэтому кубический
объём касается и сохраняемых метаданных, не только временной работы CPU.
Вход без отступов имеет `O(D)` байт. Ограничение `MAX_INLINE_DEPTH = 128`
относится к inline-парсеру, не к этой многострочной цепочке.

Замена `paths.iter().find()` на хеш-таблицу сама по себе это не исправит:
если ключом индекса остаётся заново материализуемый полный путь, кубическое
копирование сохраняется. Нужна общая структура узлов пути с родительскими
ссылками/идентификаторами и присоединением поддерева при закрытии, без
переписывания всех путей для каждого предка. Для этой цепочки целевой
объём метаданных может быть `O(D)`. Большой глубиной процесс не нагружался;
OOM или конкретный RSS этим ревью не измерялся.

### R6-F4. P2: merge-проход не соответствует заявленному O(n)

Место: `src/thin/merge.rs:21`, `:139` и `:222`;
условие запуска: `src/thin/mod.rs:44`.

`find_seen()` линейно ищет первый Object данного ключа. Для `K` различных
Object-valued siblings в одном буфере снова получается `K(K-1)/2`
проверок ключей, а не заявленный линейный проход.

Важно условие срабатывания: достаточно одного повторного открытия
где-либо в документе, чтобы `parse_events_merged()` пересобрал весь поток,
включая несвязанные с этим открытием ветви. Небольшой представитель
семейства проходит проверку Values на обоих API:

```ktav
a0.x: 1
a1.x: 1
a2.x: 1
a0.y: 2
```

При увеличении числа различных `aN` квадратичный поиск остаётся отдельно
от R6-F2: даже после индексации parser paths merge сохранит свой поиск.

Исправление: индекс `decoded_key -> buffer_id` внутри каждого merge-буфера,
а порядок вывода оставить в `items`. Цель: ожидаемое `O(E)` число операций
по событиям плюс стоимость хеширования байтов ключей, где `E` есть число
событий. Сохранить путь без merge при `reopens == 0`, порядок первого
появления и тесты анонимных compound-элементов Array из прежних раундов.
Комментарий `O(n)` сейчас неверен и должен описывать реальный алгоритм.

### R6-F5. P2: генератор бенчмарков создаёт невалидный good-input и маскирует ошибочный error-path

Место: `benches/fixtures.rs:38`, `:46`, `:49`;
потребители: `benches/parse.rs:193` и `:208`.

Проверен ровно небольшой `fixtures::small_1k()` из существующего модуля,
не переписанная копия генератора. Результат одинаков в debug/release:

| Образец | Размер | Результат `parse()` |
|---|---|---|
| `small_1k()` | 1078 байт | `UnbalancedBracket`, строка 14, span `272..273` |
| `with_bad_line(&good)` | 1088 байт | Та же ошибка на той же строке и span |

Первый `# generated benchmark fixture` по текущей spec не является
комментарием: комментарии начинаются с `##` (раздел 3.4). Он выбирает
Array root, а следующие пары становятся строковыми элементами; исходный
`}` на строке 14 приводит к отказу раньше внедрённой ошибки.
Дополнительно генератор содержит удалённые маркеры `:i/:f`. После
установления Object root строка `port_1:i 8001` уже даёт
`MissingSeparatorSpace`, так что исправить только комментарий недостаточно.

В success-группе `parse_synth` стоит `.unwrap()` над этим `Err`: группа
не может отработать как бенчмарк успешного разбора. Error-группа проверяет
лишь `is_err()` и потому принимает исходно сломанный good-input за
успешный отрицательный контроль. Она измеряла бы не тот участок обработки
ошибок, для которого предназначена.

Исправление: привести генератор к `##` и текущим plain numeric scalars;
до измерения проверять, что good-input принят как ожидаемый Object с
нужными числовыми типами. Bad-line внедрять в известную позицию Object
и проверять ожидаемую категорию/место ошибки, а не только `is_err()`:
произвольная середина документа может попасть внутрь Array или String.
Criterion и большие генераторы в этом ревью не запускались. Вывод о
невалидности входов не является результатом измерения скорости.

## Аллокации И Ускорение

Следующие возможности подтверждаются структурой вызовов, но их выигрыш
в latency, числе allocator calls и пиковом RSS не измерялся. Они не
должны подменять устранение доказанных проблем асимптотики.

### A1. P3: резервирование arena зависит от байтов входа, а не плотности событий

`src/lib.rs:142` и `src/thin/mod.rs:193` резервируют примерно `6N + 4096`
байт при `N` байтах входа, исходя из 24 байт на Event и `N/4` событий.
`src/thin/event_parser.rs:54` также задаёт ёмкость потока как `N/4 + 64`.
Для длинного комментария или одного длинного строкового поля событий
почти нет, но предварительная заявка памяти всё равно пропорциональна
всему тексту с большим множителем.

Это не две независимые заявки по `6N`: EventStream размещается в той же
arena. И это не измерение RSS; описывается политика начальной ёмкости.
Стоит проверить ограниченный начальный резерв и последующий рост по
реальному числу событий, включая контрастные документы: много коротких
полей, длинные строки, комментарии и раннюю ошибку. Порог выбирать после
измерений, чтобы не обменять снижение памяти на множество перевыделений.

### A2. P3: inline thin-path строит owned-дерево и повторно копирует данные

`src/thin/event_parser.rs:1489` сначала вызывает owned inline parser,
затем `value_to_events()` на `:1602` создаёт временный обычный `Vec<Event>`.
Все строки/числовые тела и ключи копируются в arena на `:1618`, `:1622`,
`:1626`, `:1632`; потом события переносятся в основной поток. Уже после
этого Serde строит конечный целевой тип.

Обещание в `src/lib.rs:132` и `src/thin/mod.rs:1` об отсутствии
промежуточного дерева/аллокаций на compound не описывает этот путь.
`CompactString` помогает коротким owned-скалярам, но не устраняет
контейнеры, временный поток и последующие копии.

Направление: общий inline scanner с выводом через `EventSink`, заимствующий
неизменённые срезы и выделяющий данные только для реального декодирования
или нормализации. Это заодно должно устранить расхождение R6-F1.
Не менять попутно момент вызова публичного callback или семантику ошибок.
Не ослаблять механически `DeserializeOwned`: временная arena всё равно
уничтожается при выходе из `from_str()`.

Повторные проходы `scan/split/find_matching_close` по вложенным подстрокам
дают работу порядка `O(N * D)` для соответствующих inline-цепочек.
Здесь `D <= 128` из-за текущего лимита, поэтому называть этот путь
неограниченным `O(N^2)` по размеру документа было бы неточно. Тем не менее
единый разбор границ сократит повторное сканирование и служебные `Vec`.

### A3. P3: декодирование без escapes всё равно материализует String

`src/parser/inline.rs:519` возвращает `input.to_string()` даже без `\`.
Он вызывается до классификации keyword/числа на `:315`. Для ключей
`decode_key_segment()` на `:902` также создаёт `String` без необходимости;
`src/parser/insert.rs:53` затем переносит его содержимое в `CompactString`.
Так теряется часть эффекта хранения коротких идентификаторов без heap.

В thin-пути quoted key без escapes проходит через временный `String`,
затем ещё одну копию в bump (`src/thin/event_parser.rs:986`), хотя его
содержимое после проверки можно заимствовать как срез между кавычками.

Кандидат: общий декодер с `Cow<str>` или отдельным заимствованным путём.
Обязательно сохранить whitespace внутри quoted keys и признак наличия
escape, который по spec принудительно делает значение String.
Меньшая локальная возможность: перенести `canonical_float()` на
`src/parser/inline.rs:366` внутрь `if strict`, поскольку lax-ветвь не
использует `rendered`; фактический эффект проверить, не полагаясь на
предположение о том, какие вызовы уберёт оптимизатор.

## Вердикт И Приоритеты

**Spec-тесты проходят, полное соответствие spec пока не достигнуто.**
R6-F1 отвергает разрешённый документ; нормативный остаток R5-F5 сохраняется.
Новые panic/P0 не продемонстрированы. R6-F3 имеет приоритет P1 по риску
кубического роста памяти. Доказательства R6-F2--R6-F4 показывают, что
ускорение требует не только уменьшения констант, но и
изменения представления путей и поиска в merge.

Рекомендуемый порядок работ:

1. Устранить P1: заменить полные повторно копируемые пути структурой узлов
   с индексом, решив R6-F3 и R6-F2 совместно и сохранив проверки конфликтов.
2. Исправить общий механизм поиска inline-границ и добавить независимые

3. Исправить и проверить данные бенчмарков до любых новых сравнений скорости.
4. Индексировать Object-ключи в merge, сохранив путь без повторных открытий.
5. Измерить A1--A3 на корректных представительных данных и выбрать наиболее
   полезные изменения, не меняя формат, порядок или публичные гарантии.

Для регрессионного контроля асимптотики полезны счётчики сравнений,
скопированных слотов и аллокаций на зафиксированном toolchain/target.
