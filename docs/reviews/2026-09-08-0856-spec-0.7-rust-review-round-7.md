## Найденные Проблемы

### R7-F1. P2: общий scanner сохраняет разные правила структурности opener

Место: `src/parser/inline.rs:1167`, `:1549`, `:1597`, `:1522`.
Потребители неверной границы: `src/parser/inline.rs:241` и
`src/thin/inline_emit.rs:350`.

Валидный документ:

```ktav
[{a: x[, "b}c": 2}]
```

Ожидаемый результат в JSON-нотации:

```json
[{"a": "x[", "b}c": 2}]
```

По разделу 5.8.5 значение уже началось со скаляра `x`, поэтому следующий
`[` является буквальным содержимым, не opener. По разделу 5.3.3 `}` внутри
quoted key также является содержимым.

Вместо результата `parse()` и `from_str::<serde_json::Value>()` возвращают
`MalformedInlineCompound` с сообщением о содержимом после matching closer.
Ошибка воспроизводится в debug/release. Контроль без внешней обёртки
успешно разбирается:

```ktav
{a: x[, "b}c": 2}
```

Также отвергаются `{outer: {a: x[, "b}c": 2}}` и raw-вариант
`[{a:: [x, "b}c": 2}]`. Старый воспроизводитель раунда 6
`[{a: [1, "x], "b}c": 2}]` теперь проходит, то есть речь о другом
источнике неверного scope, а не о непроверенном закрытии R6-F1.

Причина: у `FindObjQ` сохранён `OPENER_GATED = false`, тогда как основной
`ScanQ` открывает scope только в начале значения. Поэтому поиск matching
closer помещает буквальный `[` в stack как Array. На следующей запятой
он выбирает контекст этого ложного Array, перестаёт защищать quoted key
и принимает его `}` за конец Object. Вложенные parser paths доверяют
полученному `Some(close)` и не вызывают правильный scanner повторно.

Унифицирована реализация цикла, но не семантика его конфигураций. Наличие
общего `Scanner::run()` само по себе не устраняет расхождение правил.

Исправление: правила структурности opener, raw-режима и quoted key должны
быть одинаковы у всех потребителей границ. Различаться могут нужный
результат и режим проверки, но не смысл байтов. Добавить независимые
оракулы для literal `{`/`[` перед последующим quoted key, root/nested
форм и plain/raw scalars. Сохранить приоритет `BadEscapeSequence` и
не считать owned/thin parity самостоятельным доказательством conformance.

### R7-F2. P2: inline-путь всё ещё материализует дерево, а документация отрицает это

Место реализации: `src/thin/inline_emit.rs:62`, `:167`, `:286`, `:453`.
Обещания: `src/lib.rs:133` и `src/thin/mod.rs:3`.

Новый путь больше не строит owned `Value` и не копирует неизменённые
скаляры в arena. Это реальное улучшение. Однако он строит другое
промежуточное дерево:

```text
Node::Leaf(Event)
Node::Array(Vec<Node>)
Node::Object(IndexMap<Cow<str>, Node>)
```

`scan_inline_events()` сначала полностью получает `node`, затем
`emit_node()` рекурсивно обходит его. Для `arr: [[1], [2]]` промежуточная
структура содержит три Array-узла с тремя отдельными `Vec`, не только
один переиспользуемый staging buffer. Это описание структуры данных,
не измеренное число вызовов allocator после оптимизации компилятором.

Обновлённый публичный текст утверждает отсутствие промежуточного дерева
и per-compound `Vec`. В частности, `thin/mod.rs` явно отрицает оба.
Таблицы ключей действительно нужны для конфликтов и dotted-key merge,
но ими не исчерпывается текущее временное состояние.

Исправление: либо честно описать заимствованное промежуточное дерево и
оставшиеся контейнерные аллокации, либо завершить переход к событиям и
стеку scope без полного `Node` DOM. Для Array не нужна таблица имён, и
отказ от промежуточного `Vec<Node>` выглядит отдельным кандидатом на
оптимизацию. Порядок вставки Object, ошибки и момент вызова публичного
callback менять нельзя. Измерять выигрыш следует после исправления R7-F4;
более быстрый разбор из одного удаления имени `Value` не следует.

### R7-F3. P2: регистрация inline-путей повторно сканирует каждое поддерево

Место: `src/thin/event_parser.rs:1310`, `:1311`, `:1542`.

Индекс `(parent NodeId, decoded_segment)` устранил прежние линейные поиски
в таблице путей и копирование полных путей при закрытии реальных frames.
Но `register_inline_child_paths()` для каждого вложенного Object сначала
вызывает `matching_bracket()` по всему его диапазону событий, затем
рекурсивно повторяет ту же работу внутри диапазона.

Достаточно одного keyed inline Object с длинным dotted key. Небольшой
представитель семейства проверен обоими API в debug/release:

```ktav
root: {a.a.a.a.x: 1}
```

Пусть `D` означает число Object-префиксов `a` перед листом `x`.
После раскрытия пути получается цепочка из `D` Object. Поиск matching
события последовательно просматривает диапазоны длиной порядка
`3D+1`, `3(D-1)+1`, ..., `4`. Сумма составляет `Theta(D^2)` просмотров
событий при `O(D)` размере этого входа и линейном числе узлов индекса.

`MAX_INLINE_DEPTH = 128` не превращает этот конкретный случай в
ограниченный множитель: физический inline compound здесь один, а
дополнительные уровни создаёт `InsertTable::descend()` при раскрытии
dotted key, не рекурсивный разбор вложенных скобок. Большая глубина и
стресс-нагрузка не запускались; вывод об асимптотике сделан по обходам.

Это не возврат кубического хранения R6-F3. Хранение новых path nodes
линейно; квадратичной остаётся другая фаза, регистрация inline-поддерева.
Текущие счётчики index probes/node allocations не измеряют эти повторные
просмотры событий и потому не закрывают данный риск.

Исправление: пройти события один раз со стеком текущих `NodeId`,
регистрируя ключи при входе и исключая содержимое Array по глубине.
Альтернатива: один раз вычислить пары Begin/End и использовать готовые
границы. Цель для данной регистрации: ожидаемое `O(E)` число операций
плюс хеширование ключей, где `E` есть число событий. В regression-контроль
добавить счётчик фактических просмотров этой фазы, не только вызовов
индекса. Сохранить границы Array и видимость inline-детей для re-entry.

### R7-F4. P2: измеритель использует другой realloc, чем обычный System

Место: `examples/a3_measure.rs:31`, `:52`, `:327`.

`CountingAllocator` переопределяет только `alloc` и `dealloc`, но не
`realloc` и `alloc_zeroed`. Поэтому он наследует их реализации
`GlobalAlloc`: для realloc это новое выделение, копирование и освобождение,
а не вызов `System.realloc`. Это видно в
[исходнике стандартного GlobalAlloc](https://doc.rust-lang.org/src/core/alloc/global.rs.html#286-302).

Дополнительно проверены исходники установленного rustc 1.97.0:
`core/alloc/global.rs:286` и `std/sys/alloc/windows.rs:203`. Для обычных
выравниваний `System` использует `HeapReAlloc`; обёртка этот путь обходит.
Отключение `COUNTING` перед таймингами отключает счётчики, но не меняет
выбранную реализацию realloc.

Это не обнаруженная UB. Риск в методике: стоимость роста `Vec`/`String`
и относительный эффект оптимизаций могут отличаться от чистого `System`.
Результаты описывают инструментированный allocator; без оговорки их
нельзя считать замером обычного системного пути.

Исправление: прозрачно делегировать все четыре операции и явно определить
смысл счётчиков alloc/realloc/запрошенных байтов. Тайминги желательно
снимать отдельно без инструментирования. Измеритель не запускался;
численный размер смещения не установлен.

## Менее Срочные Замечания

### P3: остаток R5-F5, общий whitespace predicate подключён не везде

Место: `src/parser/insert.rs:141`, `src/thin/inline_emit.rs:202`,
`src/thin/event_parser.rs:638`, `src/render/helpers.rs:269`.

`src/whitespace.rs` теперь задаёт общий закрытый набор 25 code points
и inline-вариант без LF/CR. Однако production-код продолжает вызывать
host `.trim()/trim_start()/trim_end()` и местами `.is_whitespace()`.
Новый `inline_emit.rs` также содержит такие вызовы.

Раздел 3.3 запрещает делегирование host-классификатору даже при текущем
совпадении набора. Тест на совпадение Rust и фиксированного списка
полезен как сигнал изменения toolchain, но не делает эти пути
неделегирующими. Ошибочная классификация на Rust 1.97.0 не наблюдалась.
Нужно завершить подключение общего predicate; утверждение модуля о том,
что вся классификация уже проходит через него, пока неверно.

### P3: A1 из раунда 6, начальный резерв arena остаётся привязан к байтам входа

Место: `src/lib.rs:150`, `src/thin/mod.rs:202`,
`src/thin/event_parser.rs:69`.

Остался первоначальный резерв примерно `6N + 4096` байт и ёмкость
потока `N/4 + 64` событий, где `N` есть длина текста. Длинные комментарии
или одно длинное строковое поле дают мало событий, но большой резерв.
Это одна arena, а не две независимые заявки по `6N`.

Ограниченный начальный резерв с ростом по потребности остаётся кандидатом
на уменьшение памяти. Порог выбирать после измерений на корректном
измерителе, отдельно для плотных событий, длинных строк и ранних ошибок.
RSS и процент выигрыша в этом ревью не измерялись.

## Качество И Приоритеты

**Spec-тесты проходят, но полное соответствие spec 0.7.0 не достигнуто:**
R7-F1 отвергает разрешённый документ, а нормативный остаток R5-F5 сохраняется.
В проверенных примерах новых panic не наблюдалось. Прежний кубический
рост метаданных устранён; это не основание переносить его P1 на любую
оставшуюся возможность ускорения.

Рекомендуемый порядок:

1. Исправить смысл opener в конфигурациях поиска границ; закрепить внешние
   оракулы, а не только одинаковое поведение owned и thin.
2. Убрать повторные проходы регистрации inline-путей и считать просмотры
   событий в тестах сложности, включая синтетическую dotted-вложенность.
3. Привести публичное описание к действительной структуре inline-парсера
   либо закончить переход от `Node` DOM к событиям и стеку scope.
4. Исправить прозрачность allocator-обёртки до новых количественных
   выводов о скорости/аллокациях; затем оценивать резерв arena.
5. Завершить использование фиксированного whitespace predicate.

Общие outcome tables через `InsertTable` уменьшают дублирование правил
конфликтов. Но общий scanner с конфигурациями, сохраняющими разные
семантические правила, не даёт того же свойства автоматически. Проверки
должны соединять контексты: literal opener, quoted key, raw marker,
реальная и dotted-вложенность, последующий sibling и повторное открытие.

Для аллокаций не следует расширять `from_str` до возвращаемых заимствований
из временной arena без отдельного дизайна lifetime: существующий
`DeserializeOwned` здесь существенен. Также нельзя менять атомарность
публикации событий callback ради более раннего вывода из scanner.
