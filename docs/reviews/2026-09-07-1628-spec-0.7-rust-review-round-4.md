## English

### Findings

All four findings below reproduce through both `parse()` and
`from_str::<serde_json::Value>()`, against both debug and release libraries.
These are valid documents rejected by the shared inline scanner, not
differences caused by Serde target conversion.

#### R4-F1. P2: nested raw scalars use the outer container's closer

Location: `src/parser/inline.rs:1568` and `:1695`, `scan_inline_closer()`.

```ktav
[{a:: x}]
```

Expected: an Array containing an Object with `a = String("x")`.
Actual: `UnterminatedInlineCompound`. The reverse nesting `{a: [:: x]}`
and quoted-key variant `[{"a":: x}]` fail with the same category.
Sections 5.8.2 and 5.8.4 permit raw pairs and nested containers;
section 5.8.5 terminates a raw pair at its containing unescaped delimiter.

Both scanner branches gate a closer with `!raw || b == close`, but `close`
belongs to the outermost container. In the example, raw mode ignores the
nested `}` because the outer closer is `]`; the final `]` leaves depth at
one. The quote-free branch has no scope stack, and the quote-aware branch
also uses the outer closer and a single `raw` flag.

Remediation: track raw/scalar mode and matching delimiter per active scope.
Test both Object-in-Array and Array-in-Object, with and without quoted keys,
and with a following sibling. Do not make literal raw openers start nesting.

#### R4-F2. P2: closing a nested Array never restores the enclosing Object context

Location: `src/parser/inline.rs:1690`, `:1711`, and `:1675`.

```ktav
{a: [1], "x}": 2}
```

Expected: an Object with `a = Array[Integer(1)]` and `x} = Integer(2)`.
Actual: `MalformedInlineCompound`, reporting content after the matching
closer. Section 5.3.3 permits literal braces inside a quoted key.

`open_stack.push((b, in_key, seg_start))` stores opener bytes (`{` or `[`),
but its pop guard compares that opener directly to a closer byte (`}` or
`]`): `*k == b`. That comparison cannot succeed. After `]`, the next comma
still sees the stale Array frame, so the following Object key is scanned
as a value and its quoted `}` prematurely closes the outer Object.
The control `{a: {b: 1}, "x}": 2}` succeeds because the stale frame happens
to have the same Object kind as its parent.

Remediation: compare matching opener/closer kinds and restore the enclosing
scope state. Add sibling quoted-key tests after an Array and after mixed
nesting, covering each key delimiter and structural characters in keys.
This is independent of R4-F1: the reproducer contains no raw scalar.

#### R4-F3. P2: non-ASCII whitespace consumes the inline value-start position

Location: `src/parser/inline.rs:1586`, `:1721`, `:1041`, and `:1124`.

Use these Rust string literals to construct inputs containing an actual
U+00A0 NBSP, not a Ktav escape:

```rust
"{a:\u{a0}[1]}"
"[\u{a0}{a: 1}]"
```

Expected: respectively, Object `a = Array[Integer(1)]` and an Array
containing Object `a = Integer(1)`. Both return `UnterminatedInlineCompound`.
Sections 3.3 and 5.8.1 require U+00A0 to behave as structural whitespace;
section 5.8.5 selects a compound at the first non-whitespace code point.

The scanner preserves `value_start` only for ASCII SPACE and TAB. The first
UTF-8 byte of NBSP clears it; the actual nested opener then becomes a
mid-scalar literal. The same ASCII-only test exists in both splitting
branches, so correcting only the initial closer scan is insufficient.

Remediation: use the closed whitespace set from section 3.3 with
code-point-aware advancement. Cover every allowed inline member of that
set before a nested opener, with/without quoted keys and after commas.
LF and CR remain line terminators, not inline whitespace.

#### R4-F4. P2: a leading escape fails to commit the value to scalar mode

Location: `src/parser/inline.rs:1519` and `:1647`, escape arms in
`scan_inline_closer()`; analogous state transitions in `split_top_level()`.

```ktav
{a: \{[text}
```

Expected: Object `a = String("{[text")`. Actual: `UnterminatedInlineCompound`.
Sections 3.7 and 5.8.5 allow escaping a leading literal opener; once the
value starts as a scalar, a later unescaped `[` is literal data.

The escape arm advances past `\{` and continues without clearing
`value_start`. The next `[` is therefore treated as a nested Array opener.
There is no Array to close, so the valid enclosing Object appears unclosed.
This defeats the escape mechanism explicitly recommended by section 5.8.5.

Remediation: a recognized escape in value position consumes scalar start;
decoded bytes cannot reopen structural dispatch. Apply the same transition
to splitting and closer detection, without confusing escaped key bytes
with a value. Cover named and Unicode escapes followed by mid-scalar
openers, through both parser APIs and quote/no-quote branches.

### Findings

Все четыре дефекта ниже воспроизведены через `parse()` и
`from_str::<serde_json::Value>()` с debug- и release-библиотеками.
Общий inline scanner отвергает валидные документы; это не различия,

#### R4-F1. P2: вложенный raw-скаляр использует closer внешнего контейнера

Место: `src/parser/inline.rs:1568` и `:1695`, `scan_inline_closer()`.

```ktav
[{a:: x}]
```

Ожидается Array с Object, где `a = String("x")`.
Получается `UnterminatedInlineCompound`. Обратная вложенность
`{a: [:: x]}` и вариант с quoted key `[{"a":: x}]` дают ту же ошибку.
Разделы 5.8.2 и 5.8.4 разрешают raw-пары и вложенные контейнеры;
раздел 5.8.5 завершает raw-пару неэкранированным delimiter её контейнера.

Обе ветви scanner проверяют closer условием `!raw || b == close`, но
`close` относится к самому внешнему контейнеру. В примере raw-режим
игнорирует вложенный `}`, поскольку внешний closer равен `]`; последний
`]` оставляет depth равным единице. В quote-free ветви нет scope stack,
а quote-aware ветвь также использует внешний closer и общий флаг `raw`.

Исправление: хранить raw/scalar-режим и matching delimiter для каждого
активного scope. Проверить Object-in-Array и Array-in-Object, с quoted keys
и без них, с последующим sibling. Литеральные raw-openers не должны
открывать вложенность.

#### R4-F2. P2: закрытие вложенного Array не восстанавливает контекст внешнего Object

Место: `src/parser/inline.rs:1690`, `:1711` и `:1675`.

```ktav
{a: [1], "x}": 2}
```

Ожидается Object с `a = Array[Integer(1)]` и `x} = Integer(2)`.
Получается `MalformedInlineCompound` с сообщением о содержимом после
matching closer. Раздел 5.3.3 разрешает буквальные скобки в quoted key.

`open_stack.push((b, in_key, seg_start))` сохраняет opener (`{` или `[`),
но условие pop напрямую сравнивает его с closer (`}` или `]`): `*k == b`.
Оно никогда не выполнится. После `]` следующая запятая всё ещё видит
устаревший Array frame, поэтому следующий Object key сканируется как
значение, а его quoted `}` преждевременно закрывает внешний Object.
Контроль `{a: {b: 1}, "x}": 2}` проходит, поскольку тип устаревшего frame
случайно совпадает с Object-типом родителя.

Исправление: сравнивать соответствующие opener/closer и восстанавливать
контекст внешнего scope. Добавить sibling quoted-key cases после Array
и смешанной вложенности, для каждого key delimiter и структурных символов
в ключах. Это независимо от R4-F1: в воспроизводителе нет raw-скаляра.

#### R4-F3. P2: не-ASCII whitespace поглощает позицию начала inline-значения

Место: `src/parser/inline.rs:1586`, `:1721`, `:1041` и `:1124`.

Эти Rust-литералы создают входы с настоящим U+00A0 NBSP, не с Ktav escape:

```rust
"{a:\u{a0}[1]}"
"[\u{a0}{a: 1}]"
```

Ожидаются соответственно Object `a = Array[Integer(1)]` и Array с Object
`a = Integer(1)`. Оба возвращают `UnterminatedInlineCompound`.
Разделы 3.3 и 5.8.1 требуют считать U+00A0 структурным whitespace;
раздел 5.8.5 выбирает compound по первому непробельному code point.

Scanner сохраняет `value_start` только для ASCII SPACE и TAB. Первый
UTF-8-байт NBSP сбрасывает его, и настоящий nested opener становится
mid-scalar literal. Та же ASCII-only проверка есть в обеих splitting
ветвях, поэтому исправить только первоначальный closer scan недостаточно.

Исправление: использовать закрытый набор whitespace из раздела 3.3
с продвижением по code points. Покрыть каждый допустимый inline-член
набора перед nested opener, с quoted keys и без них, после запятых.
LF и CR остаются line terminators, не inline whitespace.

#### R4-F4. P2: начальный escape не переводит значение в scalar-режим

Место: `src/parser/inline.rs:1519` и `:1647`, escape-ветви
`scan_inline_closer()`; аналогичные переходы в `split_top_level()`.

```ktav
{a: \{[text}
```

Ожидается Object `a = String("{[text")`. Получается
`UnterminatedInlineCompound`. Разделы 3.7 и 5.8.5 разрешают экранировать
начальный literal opener; после начала скаляра следующий неэкранированный
`[` является буквальными данными.

Escape-ветвь пропускает `\{` и продолжает цикл, не сбросив `value_start`.
Следующий `[` ошибочно считается opener вложенного Array. Закрывать Array
нечем, и валидный внешний Object кажется незакрытым. Это ломает механизм
экранирования, прямо рекомендованный разделом 5.8.5.

Исправление: распознанный escape в value-позиции поглощает scalar start;
decoded bytes не должны заново включать structural dispatch. Применить
одинаковый переход в splitting и closer detection, не смешивая escaped
key bytes со значением. Покрыть named/Unicode escapes перед mid-scalar
openers, оба parser API и ветви с кавычками и без них.

### 问题

以下四个问题均已通过 `parse()` 和 `from_str::<serde_json::Value>()`
在 debug、release 两种库构建中复现。共享的 inline scanner 拒绝了合法文档，
并非 Serde 目标类型转换造成的差异。

#### R4-F1. P2：嵌套 raw 标量错误地使用最外层容器的结束符

位置：`src/parser/inline.rs:1568` 和 `:1695`，`scan_inline_closer()`。

```ktav
[{a:: x}]
```

预期：Array 包含一个 Object，其中 `a = String("x")`。
实际：`UnterminatedInlineCompound`。反向嵌套 `{a: [:: x]}` 和带引号键的
变体 `[{"a":: x}]` 也返回相同错误。第 5.8.2、5.8.4 节允许 raw 键值对
和嵌套容器；第 5.8.5 节规定 raw 键值对在所属容器的未转义分隔符处结束。

两个 scanner 分支都通过 `!raw || b == close` 判断结束符，但 `close`
属于最外层容器。示例中外层结束符是 `]`，因此 raw 模式忽略了嵌套的 `}`；
最终的 `]` 只将深度降到一。无引号分支没有作用域栈，而引号感知分支同样
使用外层结束符及单一 `raw` 标志。

修复方向：为每个活动作用域记录 raw/scalar 模式及匹配的结束符。测试
Array 中的 Object、Object 中的 Array，有无带引号键，以及后续兄弟元素。
raw 内容中的字面量起始括号不得打开嵌套作用域。

#### R4-F2. P2：嵌套 Array 结束后无法恢复外层 Object 上下文

位置：`src/parser/inline.rs:1690`、`:1711` 和 `:1675`。

```ktav
{a: [1], "x}": 2}
```

预期：Object 包含 `a = Array[Integer(1)]` 和 `x} = Integer(2)`。
实际：`MalformedInlineCompound`，提示匹配结束符后存在内容。
第 5.3.3 节允许带引号键中出现字面量括号。

`open_stack.push((b, in_key, seg_start))` 保存的是起始符（`{` 或 `[`），
但弹栈条件直接将它与结束符（`}` 或 `]`）比较：`*k == b`。
此条件不可能成立。在 `]` 之后，下一个逗号仍看到过期的 Array 栈帧，
于是后续 Object 键被作为值扫描，其引号内的 `}` 提前关闭了外层 Object。
对照输入 `{a: {b: 1}, "x}": 2}` 可以成功，因为过期栈帧的 Object 类型
恰巧与父作用域相同。

修复方向：检查起始符与结束符是否匹配，并恢复外层作用域状态。
增加 Array 和混合嵌套之后的兄弟带引号键测试，覆盖各类键引号及键中的
结构字符。此问题独立于 R4-F1，因为复现输入不含 raw 标量。

#### R4-F3. P2：非 ASCII 空白错误地消耗 inline 值的起始位置

位置：`src/parser/inline.rs:1586`、`:1721`、`:1041` 和 `:1124`。

使用以下 Rust 字符串字面量生成输入；其中是实际的 U+00A0 NBSP，
不是 Ktav 转义序列：

```rust
"{a:\u{a0}[1]}"
"[\u{a0}{a: 1}]"
```

预期分别为 Object `a = Array[Integer(1)]`，以及包含 Object
`a = Integer(1)` 的 Array。两者均返回 `UnterminatedInlineCompound`。
第 3.3、5.8.1 节要求将 U+00A0 视为结构空白；第 5.8.5 节根据第一个
非空白码点选择复合值。

scanner 仅对 ASCII SPACE 和 TAB 保留 `value_start`。NBSP 的首个 UTF-8
字节将其清除，真正的嵌套起始符因此被当作标量中间的字面量。
两个拆分分支也存在相同的 ASCII-only 检查，因此只修复初始结束符扫描
并不足够。

修复方向：按码点推进，并使用第 3.3 节的固定空白集合。
覆盖嵌套起始符前所有允许的 inline 空白成员，包括有无带引号键及逗号后
的位置。LF 和 CR 仍是行终止符，不是 inline 空白。

#### R4-F4. P2：开头的转义没有将值确定为标量模式

位置：`src/parser/inline.rs:1519` 和 `:1647`，`scan_inline_closer()`
的转义分支；`split_top_level()` 中也有类似状态转换。

```ktav
{a: \{[text}
```

预期：Object `a = String("{[text")`。实际：`UnterminatedInlineCompound`。
第 3.7、5.8.5 节允许转义开头的字面量起始括号；值一旦作为标量开始，
后续未转义的 `[` 就是字面量数据。

转义分支跳过 `\{` 后直接继续循环，没有清除 `value_start`。
下一个 `[` 因而被视为嵌套 Array 的起始符。实际上没有需要关闭的 Array，
合法的外层 Object 却被判定为未结束。这破坏了第 5.8.5 节明确推荐的
转义机制。

修复方向：值位置上的已识别转义必须消耗标量起始状态；解码后的字节
不得重新触发结构分派。拆分与结束符检测应采用一致转换，且不能混淆
转义的键字节和值。测试命名转义、Unicode 转义后出现的标量中间括号，
覆盖两个 parser API 及有无引号的分支。
