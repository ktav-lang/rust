P0 означает экстренный блокер; P1 серьёзный риск ближайшего исправления;

неоптимизированный fallback serde, оставшийся после исправления writer.

## Найденные Проблемы

### R17-F1. P3: запрос среза для inline-ключа проходит через heap String

Места: `src/de/key_deserializer.rs:68`, `:76`, `:95`.
Контрольный путь: `src/de/value_deserializer.rs:167`.
Текущее покрытие: `tests/de/owned_key_names.rs:21`, `:55`.

В новом helper и `deserialize_string`, и `deserialize_str` вызывают
`visit_owned_text`. Для `Local(Scalar)` он безусловно делает
`visitor.visit_string(s.into_string())`. Это правильно передаёт
существующий длинный буфер String-цели, но для inline Scalar создаёт
новый heap String даже тогда, когда visitor просит только срез.

Это не гипотетическая custom-оптимизация. Закреплённая compact_str
0.9.0 десериализует `CompactString` через `deserialize_str`; её
`visit_str` копирует короткое имя непосредственно inline, а
`visit_string` снова преобразует временный String в inline Scalar и
освобождает его буфер. Serde 1.0.228 также читает human-readable
`Ipv4Addr` через `deserialize_str` и FromStr visitor: результату
вообще не требуется строковый heap-буфер.

Независимая диагностика передаёт заранее созданный Object в
`de::from_value`. Test visitor извлекает один ключ без Vec/BTreeMap
результата и пропускает его Null-значение через `IgnoredAny`. Подготовка
Object, ожидаемых значений и вывод исключены из окна подсчёта.
Контроль читает такое же содержимое отдельного scalar Value через
`from_value`, то есть использует `ValueDeserializer`, не key adapter.
Это не попытка разобрать запрещённый скалярный корневой Ktav-документ.

Результаты одинаковы в debug и release:

| Цель и имя | Allocations при чтении ключа | Контроль scalar Value |
|---|---|---|
| `Scalar`, `port` | 1 | 0 |
| `Option<Scalar>`, `port` | 1 | 0 |
| `Ipv4Addr`, `127.0.0.1` | 1 | 0 |
| Visitor, возвращающий только длину `port` | 1 | 0 |
| `String`, `port` | 1 | 1 |
| `u32`, `42` | 0 | 0 |
| `String`, heap-backed имя в 52 байта | 0 | 0 |
| `Scalar`, heap-backed имя в 52 байта | 0 | 1 |

Во всех случаях результаты десериализации правильные. Последняя строка
показывает полезную сторону нового reader: длинный Scalar тоже может
получить буфер без копирования. Нельзя просто вернуть безусловный
`visit_str` для всех owned-ключей и считать оптимизацию завершённой.

До `c5691d0` key `deserialize_str` передавал срез, поэтому для первых
четырёх случаев этого String не было. Новые тесты проверяют String-цель
и непосредственно числовой u32, но не `Scalar` или строковый FromStr
visitor; эти группы используют другие методы serde.

Рекомендация: в `deserialize_str` выбирать способ доставки с учётом
того, есть ли уже heap-буфер. Для inline/non-heap имени передавать
`visit_str`, а существующий heap Scalar можно по-прежнему отдавать
через `visit_string`. `deserialize_string` сохраняет явный запрос
владения, numeric-методы продолжают разбирать срез. Не выдавать
`visit_borrowed_str` для локально принадлежащего reader буфера.
Закрепить allocation-матрицу коротких Scalar/IP/Option-ключей и
длинных String/Scalar-ключей, чтобы устранение одного расхода не
возвращало другой.

Для K таких коротких ключей возможна экономия K временных выделений.
Асимптотика обработки документа не меняется; это снижение константы
и allocation churn, не обещание измеренного ускорения по времени.

### R17-F2. P3: общий key writer не переопределяет `collect_str`

Места: `src/ser/text_serializer.rs:493`, `:499`, `:511`.
Заявление об отсутствии промежуточного String: там же, `:470`.
Текущий allocation-тест: `tests/key_name_alloc.rs:71`.

Прямой `serialize_str` теперь пишет в Scalar и действительно обходится
без временного String. Но `KeyOnlySer` наследует default `collect_str`
из serde 1.0.228. Он вызывает `self.serialize_str(&value.to_string())`:
до входа в исправленный метод уже создан heap String, затем имя ещё
раз копируется в Scalar. Для длинного имени возникает и второй
строковый heap-буфер.

Этот путь доступен обычному `Serialize`, который делегирует
`serializer.collect_str(self)` для Display-идентификатора. Он также
используется самой serde для `std::fmt::Arguments`: достаточно
вызвать `serialize_entry(&format_args!("port"), "v")` у SerializeMap.
Не требуется новая зависимость или заведомо неоптимальная ручная
сериализация через `format!(...)` в вызывающем коде.

Измеренные allocations полного вызова writer на одноэлементном map:

| Имя и способ его передачи | Direct, обычный str | Direct, collect_str | Owned, обычный str | Owned, collect_str |
|---|---|---|---|---|
| `port`, custom Display key | 1 | 2 | 2 | 3 |
| То же `port`, `fmt::Arguments` | 1 | 2 | 2 | 3 |
| Display key в 52 байта | 2 | 3 | 3 | 4 |

Debug/release совпали; тексты, Value и результаты parse совпадают
между контрольным и Display-путями. Количество базовых allocations
включает выходной String либо структуру ObjectMap; важен дополнительный
один вызов на тот же самый ключ. Это не регрессия `618a10c`: fallback
существовал раньше. R16-F2 закрыт для прямого `serialize_str`, но
универсальное утверждение нового комментария о любом коротком имени
пока сильнее фактической реализации.

Рекомендация: переопределить `collect_str` в `KeyOnlySer`, форматируя
Display непосредственно в существующий `&mut Scalar` через `fmt::Write`
и преобразуя ошибку форматирования в текущую serializer error.
Это сохраняет Display-написание имён и не затрагивает канонизацию
Float-значений. Добавить differential allocation-тест для одинакового
имени через str, Display-wrapper и `fmt::Arguments`, отдельно короткого
и длинного. Для K Display-ключей убирается K промежуточных String;
глобальное O записи остаётся прежним.

## Закрытие Раунда 16 И Качество

| Находка | Статус |
|---|---|
| R16-F1 | Закрыта: все 32 прежних чтения Option-ключей проходят обоими readers/writers, включая `Some("null")`, вложенный Some, enum и newtype. Отдельные обязательные assertions thin/owned тоже проходят. |
| R16-F2 | Закрыта для описанного прямого String-key пути: имя пишется сразу в Scalar, новый allocation-тест проходит. Остаточный serde fallback выделен как R17-F2. |
| R16-F3 | Закрыта: длинный owned String-ключ сохраняет адрес буфера; независимый контроль и новый regression-тест проходят. Короткий numeric parse не аллоцирует. Побочный расход других short-key целей описан в R17-F1. |

Новые inverse-тесты проверяют обе стороны преобразования, не только
полученное имя. `None`, `Some(None)` и дополнительная вложенность None
по-прежнему отвергаются writer. Literal `null` остаётся именем, а не
отсутствующим ключом. Передача owned Scalar не удлиняет время жизни
среза: borrowed event-путь и локальное владение разделены корректно.
Публичные `from_str` и `from_value` сохраняют `DeserializeOwned`.

Новый `tests/key_name_alloc.rs` размещён отдельным test binary с одной
test-функцией; другие integration-тесты не делят с ним глобальный
счётчик. Проверяет реальный вызов allocator, не wall-clock порог.
Его `unsafe impl GlobalAlloc` (`:46`) просмотрен: pointer/layout и
размер realloc без изменения передаются System, счётчик атомарный,
логирования или выделений внутри allocator нет. Здесь не найдено
нарушения ownership/layout; Miri не запускался. Address-контроль
owned-ключа полезен против прежнего copy-before-drop механизма, но
не заменяет allocation-матрицу для других целевых типов.

Проверены обязательства §5 о строковых именах Object, §5/§5.2 о
числовом домене и классификации, §5.9.8/§5.9.10 о canonical numbers
и именах, §8.3 о canonical fixed point, а также serde roundtrip из
README. Нормативный текст и parser/writer grammar в этом diff не
менялись; текущий conformance corpus проходит без исключений.
Повторены прежние 12 key cases, четыре Float-ключа, 18 typed и
34 Integer Value проверки, 92 Float проверки. Ошибок, расхождений
Value, битов f32 или canonical idempotence не обнаружено.

Глобальные структуры данных не менялись. Сортировка C inline-границ
O(C log C) и binary search в `src/parser/inline.rs`, резерв arena по
длине исходника в `src/lib.rs` / `src/thin/mod.rs` и две временные
строки scientific-ветки `canonical_float` остаются прежними
кандидатами для профилирования. Это не новые находки или доказанные
bottleneck текущего workload. Обе новые P3 позволяют убрать конкретные
промежуточные allocations без переписывания индекса или грамматики.
