# Ревью Rust-реализации Ktav spec 0.7

Дата: 2026-09-07.

Проверенный Rust commit: `1881ae6b726784f35763fa6ad05a370cd116db6d`.
Подключённый spec commit: `7f05a1b39a773d22f5e9a927d7c55c8c51d82de4`.
Рабочее дерево перед проверкой было чистым.

## Вердикт

Штатные тесты проходят, но считать поддержку spec 0.7 завершённой нельзя.
Найдены два P1 и три P2: panic на допустимом Integer, неверный root dispatch
в thin-парсере, отказ на допустимых dotted keys, неверные категории ошибок
и недостаточно строгий числовой оракул conformance-runner.

Дополнительно обнаружены отсутствие поддержки корневых последовательностей
в Serde-сериализаторе и падающий gate форматирования.

## Findings

### F1. P1: prefixed i64::MIN вызывает panic

Место: `src/parser/classify.rs:251`, `parse_prefixed_int()`.

Вход `x: -0x8000000000000000\n` вызывает panic
`attempt to negate with overflow` через оба API: `parse()` и `from_str()`.
Также воспроизведено для `x: -0o1000000000000000000000\n`.

Magnitude `2^63` проходит проверку диапазона. Затем `val as i64` уже даёт
`i64::MIN`, и выражение `-(val as i64)` переполняется. Это допустимые
представления минимального Integer, а не некорректный пользовательский ввод.
Panic подтверждён на debug-сборке; release-профиль имеет другую политику
overflow checks, поэтому дефект зависит от профиля сборки.

Рекомендация: отдельно возвращать `i64::MIN` для magnitude `2^63`, как уже
делает decimal-путь. Добавить проверки hex, octal и binary на обоих API,
включая соседние значения внутри и вне диапазона.

### F2. P1: from_str неправильно обрабатывает явную корневую обёртку

Места: `src/thin/event_parser.rs:45`, `:150`, `:305`.

Воспроизведено:

- `from_str::<serde_json::Value>("[1, 2]\n")` возвращает `[[1, 2]]`;
- `from_str::<Vec<i64>>("[1, 2]\n")` возвращает
  `expected i64, got Some(BeginArray)`;
- inline Object root, например `{a: 1}`, отвергается как `InvalidKey`;
- valid fixtures с явным многострочным Object root также отвергаются,
  а Array root получает дополнительный уровень вложенности.

Thin-парсер создаёт неявный root event, определяя Object/Array по первой
строке, но затем обрабатывает корневую обёртку как обычную строку внутри
этого root. Owned-парсер эти fixtures принимает корректно.

Рекомендация: реализовать отдельные состояния явного корня и top-level
inline document, включая проверку оставшегося содержимого после закрытия.
Прогонять все valid fixtures через `parse_events()` и `from_str()`, а не
только через owned `parse()`.

### F3. P2: thin-парсер отвергает разрешённое продолжение dotted keys

Место: `src/thin/event_parser.rs:788`, `register_synthetic_prefix()`.

Два готовых valid fixture проходят через `parse()`, но отвергаются через
`from_str()`:

- `spec/versions/0.7/tests/valid/dotted_keys/reopen_after_sibling.ktav`:
  `a.b: 1\nc: 2\na.d: 3` даёт `KeyPathConflict / SyntheticReopen`;
- `spec/versions/0.7/tests/valid/dotted_keys/extend_explicit_object.ktav`:
  `a: {\n    x: 1\n}\na.y: 2` даёт `KeyPathConflict / BlockedByValue`.

Линейная событийная модель закрывает объект раньше, чем становится известно,
будут ли следующие строки его расширять. Текущее ограничение модели нельзя
выдавать за ошибку документа, который спецификация разрешает.

Рекомендация: предусмотреть буферизацию или корректный fallback для таких
объектов; добавить обе fixtures в проверку thin/Serde-пути.

### F4. P2: invalid conformance не проверяет категории ошибок

Места: `src/parser/classify.rs:58`, `tests/spec_conformance.rs:333`.

Runner проверяет `ktav::parse(text).is_ok()`, но не сравнивает ошибку с
`expected_error` JSON-оракула. Между тем spec 0.7 §8.1 требует совпадения
категории.

Внешняя проверка существующего invalid corpus подтвердила пять несовпадений
на owned API:

| Fixture относительно `spec/versions/0.7/tests/invalid/` | Ожидается | Получено |
|---|---|---|
| `bad_escape/unknown_sequence_before_missing_closer.ktav` | `BadEscapeSequence` | `UnterminatedInlineCompound` |
| `inline/leading_bracket_before_separator.ktav` | `MalformedInlineCompound` | `UnterminatedInlineCompound` |
| `inline/leading_whitespace_bracket_before_separator.ktav` | `MalformedInlineCompound` | `UnterminatedInlineCompound` |
| `inline/malformed_trailing_content_array.ktav` | `MalformedInlineCompound` | `UnterminatedInlineCompound` |
| `inline/malformed_trailing_content_object.ktav` | `MalformedInlineCompound` | `UnterminatedInlineCompound` |

Например, `x: [1] junk` имеет закрывающую скобку, но получает категорию
незакрытого compound. В `x: [a\q` неизвестный escape должен иметь приоритет
над отсутствием closer, однако возвращается `UnterminatedInlineCompound`.

На thin API несовпадений больше: отдельно зафиксированы неверные категории
для `inline/backslash_at_eol.ktav`,
`inline/unterminated_via_unclosed_quoted_key_top_level.ktav`,
`top_level/content_after_inline_root.ktav` и
`top_level/multi_inline_objects_jsonl_style.ktav`.

Рекомендация: сравнивать категории на обоих parser API, затем исправить
matching-close и escape-precedence logic. Различать category check и проверку
человеко-читаемого текста ошибки.

### F5. P2: числовой оракул допускает потерю типа и точности

Место: `tests/spec_conformance.rs:104`, `json_eq_ordered()`.

При различающихся текстовых формах оба числа приводятся к `f64` и
сравниваются через `==`. Поэтому comparator допускает:

- равенство Integer `1` и Float `1.0`;
- равенство Float `0.0` и `-0.0`;
- равенство разных больших Integer, округляющихся в одно значение `f64`.

Это статически подтверждённый пробел тестового оракула, а не утверждение,
что parser уже допускает все перечисленные потери на текущих fixtures.

Рекомендация: сначала сверять Value kind, Integer сравнивать точно,
Float сравнивать в заявленном binary64-домене с сохранением знака нуля.
Применять boundary exemptions только к указанным листьям и классам границ.

## Дополнительные улучшения

`src/ser/text_serializer.rs:294`: `RootSer::serialize_seq()` и tuple-методы
всегда возвращают `top-level value must be an object`. Воспроизведён отказ
`to_string(&vec![1i64, 2])` и пустого `Vec<i64>`. Это документированное
ограничение данной поверхности, но для полноценной поддержки root Array
через Serde его нужно снять и добавить round-trip через `from_str()`.

`cargo fmt --check` завершается с кодом 1. Среди затронутых файлов:
`src/parser/inline.rs`, `src/parser/parser.rs`, `src/parser/tests.rs`,
`tests/quoted_keys.rs`, `tests/quoted_keys_thin.rs`.
Форматирование входит в обязательный CI gate `.github/workflows/ci.yml`.

Основной архитектурный риск: правила грамматики продублированы между owned
parser и thin event parser и уже разошлись. Приоритетнее всего установить
общий corpus gate для обоих API, затем выделять общие правила распознавания
и определения категорий ошибок. Наличие большого количества собственных
unit tests не заменяет этот gate.

Среда: Windows x86_64, `rustc 1.97.0 (2d8144b78 2026-07-07)`.

| Canonical fixtures | 202 прошли |

| `cargo fmt --check` | FAIL |

Дополнительный небольшой воспроизводитель вне репозитория вызвал публичные
API из собранной библиотеки. Он подтвердил panic, неверный Array root,
отказы thin API на valid fixtures и несовпадения error categories.
Различия только текстовой записи эквивалентных Float в JSON не считались
ошибками реализации.

Проверка применяла подход `rust-intel` к семантическому соответствию и
качеству оракулов. Это целевое ревью реализации 0.7, не полный аудит всех
модулей безопасности, зависимостей и производительности.

MSRV 1.71, Linux/macOS, Miri и supply-chain audit в этом раунде не запускались.
Зелёный release-suite не покрывает отдельный найденный prefixed-i64::MIN
репродьюсер и не закрывает debug panic.

Исходники и тесты репозитория в ходе ревью не изменялись. Единственное
добавление по последующему запросу пользователя: настоящий отчёт.
