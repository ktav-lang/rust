## Найденные Проблемы

R5-F1--R5-F4 воспроизведены через `parse()` и полный
`from_str::<serde_json::Value>()` с debug- и release-библиотеками.
Это находки данного раунда, не утверждение, что все они внесены тремя
последними исправлениями. R5-F5 нарушает нормативное требование к реализации;
неверная классификация whitespace на текущем toolchain не заявляется.

### R5-F1. P2: scanner без кавычек использует key-контекст внешнего контейнера

Место: `src/parser/inline.rs:1603`, `:1620` и `:1653`.

```ktav
[{a: 1, b: [2]}]
```

Ожидается Array с Object `a = Integer(1), b = Array[Integer(2)]`.
Получается `UnterminatedInlineCompound`. Кавычки только у первого ключа
делают тот же документ допустимым:

```ktav
[{"a": 1, b: [2]}]
```

Ключи эквивалентны по разделу 5.3.3. Разделы 5.8.2 и 5.8.4 разрешают
вложенный Array во второй паре. Fast scanner на запятой проверяет внешний
флаг `object`, а не текущий scope. При Array root он не включает `in_key`
для ключа `b` вложенного Object; двоеточие этой пары не включает
`value_start`, и `[` не начинает вложенность. Quote-aware ветвь на строке
1772 корректно обращается к `open_stack`.

Обратный случай также ломается: `{a: [1, x: [text]}` должен содержать
Array из `Integer(1)` и `String("x: [text")`, но запятая вложенного Array
ошибочно включает Object key-контекст. `{"a": [1, x: [text]}` проходит.
Комментарий о ненужности восстановления fast-path состояния неверен:
key-контекст влияет на двоеточия и при полном отсутствии кавычек.

Исправление: определять тип контейнера и key/value-переходы по активному
frame в обеих ветвях. Добавить случаи второй и последующих пар, а также
метаморфные проверки: кавычки у эквивалентного ключа не должны менять
Value или допустимость документа.

### R5-F2. P2: буквальное начальное двоеточие не поглощает scalar start

Место: `src/parser/inline.rs:1591` и `:1756`.

```ktav
{a: :[text}
```

Ожидается Object `a = String(":[text")`. Получается
`UnterminatedInlineCompound`. `{"a": :[text}` и `[:[text]` ломаются так
же; проблема не ограничена ветвью без кавычек.

Двоеточие-разделитель и начальное двоеточие скаляра разделены пробелом,
поэтому это не pair marker `::`. По ordered inline-value alternatives
раздела 4 и разделу 5.8.5 значение начинается с `:`, не с `[`, и сразу
становится скаляром. Следующий `[` является литералом. Однако ветвь
`b':'` в этом случае не меняет key-контекст и не сбрасывает `value_start`.
Следующий `[` ошибочно открывает вложенный Array, и внешний Object
кажется незакрытым.

Исправление: отличать реальные pair separators/raw markers от двоеточий
внутри значения. Обычное начальное двоеточие должно фиксировать scalar-режим
так же, как начальная буква или распознанный escape. Покрыть plain/raw
разделители, whitespace между двоеточиями, Array items и обе ветви scanner,
не придавая mid-value двоеточиям структурного смысла.

### R5-F3. P2: raw-режим поглощает неэкранированный mismatched closer; regression-оракулы неверны

Место: `src/parser/inline.rs:1625` и `:1793`;
оракулы: `tests/inline_nested_scopes.rs:134` и `:154`.

```ktav
{a:: x]}
```

Получается успешный Object `a = String("x]")`. Вариант `{"a":: x]}`
и вложенный `[{a:: x]}]` также принимаются. Эти входы должны отвергаться,
а не превращаться в String с неэкранированным terminator внутри.
`<inline-raw-scalar>` в разделе 4 прямо завершается на первом
неэкранированном `,`, `}` или `]` (`spec.md:588`), независимо от того,
какому контейнеру соответствует этот байт. Raw-режим делает начальные
openers буквальными, но не отменяет грамматику завершения скаляра.

Условие `!raw || b == close_for_kind(...)` считает другой тип closer
обычным содержимым. Новые тесты прямо утверждают, что crossed closer
входит в String, например для `[{a:: x]}]`. Поэтому корректное исправление
должно заменить эти неверные positive-оракулы. Экранированный положительный
контроль валиден и уже проходит:

```ktav
{a:: x\]}
```

Исправление: завершать raw-скаляр на всех предусмотренных грамматикой
неэкранированных terminators, отдельно диагностируя несовпадающую
структуру. Сохранить валидные raw-opener и nested-raw случаи, дополнив их
отрицательными unescaped-closer и положительными escaped-closer случаями.

**Уточнение рекомендации раунда 4:** хранить состояние scope необходимо,
но трактовка завершения raw как *только* собственного closer текущего
scope была чрезмерно широкой. Этот отчёт заменяет данную часть
рекомендации: реализация и оракулы обязаны следовать явному production
раздела 4. Предыдущее ревью не является независимым оракулом spec.

### R5-F4. P2: хвост после закрытого вложенного compound получает неверную категорию

Место: `src/parser/inline.rs:236`, `:253`, `:262` и `:278`.

```ktav
{a: [1] junk}
```

Ожидается `MalformedInlineCompound`. Получается
`UnterminatedInlineCompound`. То же происходит для `{a: {b: 1} junk}`
и `[[1] junk]`. Контроль без inline-вложенности `a: [1] junk` корректно
возвращает `MalformedInlineCompound`, а `{a: [1]}` успешно разбирается.

Разделы 6.11 и 6.12 явно различают отсутствие matching closer и
непробельное содержимое после существующего closer. В
`parse_inline_value_raw` вызов `find_matching_close` возвращает
`Some(close)`, но `close != trimmed.len() - 1` сводится к тому же `false`,
что и отсутствие closer. Оба исхода затем дают unterminated-категорию.
Это вложенный вариант проблемы диагностики из раунда 1, не падение
исправленных top-level fixtures.

Исправление: сохранять различие found/missing/invalid, а не сводить его
к boolean. Применять одинаковый выбор категории на каждом уровне
вложенности; дополнить trailing-content fixtures обёртками Object-value
и Array-item на обоих публичных parser paths.

### R5-F5. P3: фиксированный класс whitespace делегируется runtime

Место: `src/parser/inline.rs:618`, особенно `:628`.

`inline_whitespace_at()` вызывает `ch.is_whitespace()` для не-ASCII code
points. Раздел 3.3 прямо устанавливает MUST NOT для делегирования
host Unicode-whitespace primitive, даже если тот сейчас совпадает с
закрытым набором; текущее точное совпадение Rust приведено как пример.
Комментарий helper использует то же совпадение для обоснования
противоположного решения.

На Rust 1.97.0 неверная классификация не наблюдалась. Это менее срочный
нормативный вопрос стабильности, не подтверждённая runtime-регрессия.
Нужен фиксированный predicate для 25 code points и его line-bounded
вариант без CR/LF для scanning и trimming. Существующие host-based trim
sites требуют той же политики. Новый тест
`whole_whitespace_set_before_nested_opener` покрывает 14 из 23 inline
members, пропуская U+2001--U+2009; следует перечислить все элементы и
соседние non-members, а не полагаться только на границы диапазона.

## Вердикт И Качество

**NO-GO для полного соответствия spec 0.7.0: четыре P2 и один P3.**
Новые P0/P1 не продемонстрированы. Четыре основных воспроизводителя
раунда 4 теперь дают ожидаемые Values в обоих API и профилях:

| Finding раунда 4 | Исправление | Результат |
|---|---|---|
| R4-F1: closer вложенного raw | `4b28b21` | Основные валидные случаи проходят; R5-F3 исправляет чрезмерно широкую трактовку raw termination |
| R4-F2: Object-контекст после закрытия Array | `4b28b21` | Исходный quoted-key случай проходит; R5-F1 выявляет пробелы fast-path контекста |
| R4-F3: whitespace перед nested opener | `f9d1f3a` | NBSP-воспроизводители проходят; R5-F5 касается нормативного контракта classifier |
| R4-F4: escape в начале скаляра | `0bdd84a` | Исходный воспроизводитель проходит |

Покрытие выросло с 887 до 915 тестов на профиль. Новые scope/escape
проверки исследуют реальные owned Values, events и отдельные typed
результаты. Но независимые scanner-реализации всё ещё расходятся в
key/value-состоянии, scalar start, raw termination и выборе ошибок.
Ключевая проблема качества не в числе тестов: часть новых assertions
закрепляет нарушение грамматики, а семантически нейтральные кавычки
у ключа меняют допустимость документа.

Приоритет: общая scoped-модель scanner и оракулы из spec. Quote opacity
должна оставаться только у key segments; завершение скаляра следует
отделить от распознавания compound opener; структурированные исходы
сканирования нужно сохранять при рекурсивном разборе. Добавить короткие
комбинации контекстов с положительными и отрицательными контролями.
Совпадение owned/thin и self-roundtrip сами по себе conformance не
доказывают. Производительность не измерялась; бенчмарки и синтетическая
стресс-нагрузка не запускались.
