## Найденные Проблемы

### R15-F1. P2: типизированные ключи читаются разными serde-путями по-разному

Места: `src/de/map_access.rs:27`, `:31`;
`src/thin/event_deserializer.rs:455`, `:639`, `:654`, `:713`.
Пробел в тестах: `tests/edge_cases/keywords_in_maps.rs:63`.

Owned `MapDe` передаёт имя ключа в стандартный serde `StringDeserializer`,
который не выполняет числовое преобразование строки по запросу целевого
типа. Thin-путь использует собственный `BorrowedStrDeserializer`:
часть numeric/bool методов реализована, а i128/u128, enum и newtype
перенаправляются в `deserialize_any`, то есть получают строковый visitor.
Это разные контракты для одного и того же Ktav Object.

Минимальный воспроизводитель:

```rust
use std::collections::BTreeMap;
let text = "42: v\n";
let thin: BTreeMap<u32, String> = ktav::from_str(text).unwrap();
let owned: BTreeMap<u32, String> =
    ktav::de::from_value(ktav::parse(text).unwrap()).unwrap();
assert_eq!(owned, thin);
```

Thin возвращает `{42: "v"}`, owned возвращает
`Err(Message("invalid type: string \"42\", expected u32"))`.
Вариант `de::from_value(ser::to_value(&map))` также отвергается.

Матрица чтения проверенного текста / Value:

| Целевой тип ключа | `from_str` | `de::from_value` |
|---|---|---|
| String, char | OK | OK |
| u32, i64, u64 | OK | Ошибка типа строки |
| bool | OK | Ошибка типа строки |
| i128/u128, включая `-1`/`1` | Ошибка типа строки | Ошибка типа строки |
| Unit enum `Tag::Alpha` | Ошибка: ожидался enum | OK |
| Newtype `struct Id(u32)` | Ошибка: ожидался tuple struct | Та же ошибка |

Все эти имена допустимы в Ktav. Домен Integer для значений здесь
не ограничивает имя: ключ `340282366920938463463374607431768211455`
является строковым именем, а преобразование в u128 есть запрос serde.
Это не повод расширять числовую классификацию parser.

Проверены root maps с 12 представителями типов/границ; результаты
debug/release совпали. Отдельный assertion успешного owned-чтения
u32 действительно падает в обоих профилях. Существующий тест числовых
ключей проверяет только `to_string -> from_str`, поэтому он зелёный.
Новые тесты раунда 14 касаются числовых значений, не этих адаптеров.

Исправление: согласовать key-deserializer policy для owned и thin,
включая точные i128/u128, bool, unit enum и делегирование newtype.
Общие правила преобразования лучше не поддерживать в двух независимых
списках методов. Не превращать каждое имя в число в `deserialize_any`:
для String-ключа исходное имя должно сохраняться. Добавить матрицу
обоих read API, обоих writer API, вложенных maps, ошибок диапазона и
нечисловых имён. Сохранить текущую поддержку строковых/char ключей.

### R15-F2. P2: key-only сериализаторы меняют модель документа при смене API

Места: `src/ser/map_serializer.rs:20`;
`src/ser/text_serializer.rs:427`, `:469`, `:490`, `:521`.
Заявленная близость путей: `src/ser/text_serializer.rs:1`.

Прямой путь использует `KeyOnlySer`, а `ser::to_value` сериализует ключ
через обычный `ValueSerializer` и извлекает scalar payload. Поэтому
преобразование имени зависит от выбора API, а нормализация числовых
значений ошибочно определяет текст Float-ключа во втором пути.

Для воспроизводителя достаточно пользовательского `Serialize`, который
создаёт map и вызывает `serialize_entry(&1.0_f64, "v")`. Оба writer
успешны, но результаты различны:

```ktav
1: v
```

```ktav
"1.0": v
```

После parse это Object с именем `"1"` против Object с именем `"1.0"`.
Это не допустимая разница написания Float-значения: имена являются
строками, и canonical emit не может переименовывать поле.

| Исходный ключ | Имя через `to_string` | Имя через `to_value` + writer |
|---|---|---|
| `1.0_f64` | `1` | `1.0` |
| `1e20_f64` | `100000000000000000000` | `1e20` |
| `1e13_f32` | `10000000000000` | `10000000000000.0` |
| `1.5_f64`, контроль | `1.5` | `1.5` |

Расходится также множество принимаемых типов: bool-ключ успешно
пишется `to_string`, но `to_value` возвращает
`map keys must serialize to strings`. Для i128/u128 обратная ситуация:
`to_value` создаёт корректное строковое имя, но `KeyOnlySer` не имеет
128-битных методов и получает default-ошибку serde `is not supported`,
даже для `1_u128`. Это отдельный writer-side пробел помимо R15-F1.

Вывод debug/release совпал. Независимый assertion равенства двух
разобранных документов действительно падает на Float-ключе `1.0`.
Числовые значения в документе, исправленные в предыдущих раундах,
при этом не затронуты: дефект находится в преобразовании имени.

Исправление: выделить общую политику сериализации имени ключа для
обоих путей, не переиспользуя нормализацию Value-чисел как неявную
нормализацию имён. Явно определить принимаемые scalar-like типы,
поддержать их симметрично или симметрично отклонять. Закрепить не
только typed roundtrip, но и равенство разобранных Object и имён
между writer-путями. Не менять уже строковые ключи вроде `"1.0"`.

### R15-F3. P3: диапазон native integer проверяется через повторный text parse

Места: `src/ser/value_serializer.rs:34`, `:37`, `:108`, `:120`, `:123`;
`src/parser/classify.rs:214`, функция `parse_decimal_int`.

Новый `int_value_in_i64_domain` сначала форматирует u64/u128/i128
через `itoa`, затем запускает `try_parse_integer` только ради ответа,
помещается ли исходное число в i64. Общий parser проверяет знак,
base prefixes, underscores и заново накапливает число с checked
арифметикой. Эти синтаксические проверки не нужны для известного
native integer, только что отформатированного `itoa`.

При фиксированном i64-домене достаточно нативной проверки
`i64::try_from(v).is_ok()` либо эквивалентного сравнения диапазона,
после которой число всё равно форматируется ровно один раз. Это
сохраняет текущую политику Integer внутри домена / String снаружи.
Доменную проверку можно вынести в общий helper без текстовой грамматики.

Это убирает повторный проход по десятичным цифрам, но не меняет
асимптотику всего writer: разрядность ограничена 64/128 битами,
а форматирование и запись цифр всё равно необходимы. Промежуточного
heap String сейчас нет; экономия аллокаций здесь не заявляется.
Это P3 возможность сократить лишнюю работу, не измеренный performance
regression и не основание для обещания процентов ускорения. Сохранить
граничные tests и сравнение с parser, но не требовать вызова конкретной
parser-функции как части семантического контракта тестов.

### R15-F4. P3: вводный Numbers не синхронизирован с исправленными примерами

Места: `README.ru.md:78`, `:80`; `README.zh.md:72`, `:74`;
`README.md:87`, `:91`.

Вводные RU/ZH-разделы по-прежнему утверждают, что числа на Value-уровне
есть строки. Исправленный раздел с примерами ниже уже утверждает
обратное. В EN типы названы правильно, но сказано, что Integer/Float
хранят точный исходный текст; на деле хранятся нормализованные payload.

Проверенный пример:

```ktav
i: +1_000
f: 1.0e+2
```

Получаются `Integer("1000")` и `Float("100.0")`, не String и не
исходные написания. Вывод совпадает в debug/release и соответствует
§5/§5.2/§5.9.8: сохранение исходного литерала не является контрактом.

Исправление: атомарно обновить эти вводные разделы EN/RU/ZH, различая
числовое значение, нормализованный payload и исходное написание;
описать i64-границу Integer и текущую String-политику `to_value` для
более широких native integers. R14-F3 поэтому закрыт частично:
его конкретные примеры, event root и внутренний cursor-header исправлены,
но прежняя модель осталась в другом разделе того же README.

## Закрытие Раунда 14 И Производительность

**R14-F1 закрыт для числовых значений.** Все 18 прежних чтений
i128/u128 теперь успешны в debug/release с обязательными assertions.
Новые тесты проверяют MIN/MAX, raw markers, Object/Array, owned/thin,
переполнение и отрицательный unsigned. Остаток по map keys вынесен
в R15-F1/F2: он использует другие serde-адаптеры.

**R14-F2 закрыт.** Прежние 34 Integer Value проверки дают ноль
расхождений вместо 26, с равенством Value и стабильным canonical emit.
Принята String-политика вне i64; parser-домен и conformance не расширены.
Прямой `to_string` сохраняет bare decimal, Value-путь использует `::`
для этих String, но оба читаются в тот же Value и нужный native integer.
Следует также уточнить прежний byte-identity комментарий прямого writer:
scientific Float теперь не единственное расхождение написаний.

**R14-F3 частично закрыт**, см. R15-F4. Исправленные примеры и event
root проходят новые integration-тесты; обе doc-сборки чистые.
Дополнительно повторены 92 Float проверки прежнего раунда:
Value equality, биты, strict acceptance и canonical idempotence сохранены.

Новых оснований менять глобальные структуры данных не получено.
`O(C log C)` компонент индекса C inline-границ, резерв arena по длине
исходника и две временные строки scientific-ветки `canonical_float`
остаются прежними профильными кандидатами, не новыми находками.
Multiline `Vec` не возвращён. В исправлении owned key reader стоит
также не материализовать `key.into_string()` ради числового преобразования,
если достаточно среза из существующего Scalar; фактические allocator
counts в этом раунде не измерялись.
