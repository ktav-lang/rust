## Найденные Проблемы

### R8-F1. P2: вложенные Array не используют общий буфер событий

Место: `src/thin/inline_emit.rs:371`, `:437`, `:438`, `:447`.
Описание, которому код не соответствует: `src/thin/inline_emit.rs:310`,
`src/lib.rs:152`, `src/thin/mod.rs:16`.

`Vec<Node>` для Array действительно удалён. Однако при обработке Array
внутри другого Array родитель вызывает `scan_inline_value_trimmed()`,
который создаёт новый `Vec<Event>`, заполняет его рекурсивно и возвращает
`Node::Array(events)`. Затем родитель копирует весь блок через
`buf.extend_from_slice(&events)`.

Таким образом, комментарий о рекурсии вложенных Array в тот же буфер
не описывает фактический путь. Блоки создаются не только для Array,
непосредственно являющихся значением Object-member.

Для цепочки из `D` Array с одним скалярным листом, например `[[[[1]]]]`,
дочерние блоки содержат `3, 5, ..., 2D-1` событий. Число копируемых
элементов только на этих соединениях:

```text
3 + 5 + ... + (2D - 1) = D^2 - 1
```

Это `Theta(D^2)` копирований структур `Event` и роста суммарно запрашиваемых
ёмкостей, отдельно от поиска текстовых границ. Байты строк при этом не
копируются заново: события несут ссылки. Квадратичный пиковый RSS не
заявляется: дочерние буферы освобождаются при возврате, и пик живых
буферов для этой цепочки может оставаться линейным по `D`.

Глубина физической inline-вложенности ограничена 128; речь о стоимости
внутри допустимого диапазона, а не о неограниченном `O(N^2)` для любого
документа. Кэш границ этот отдельный поток копирования не устраняет.

Исправление: Array-элементы, включая вложенные Array, разбирать в общий
неопубликованный буфер. Сохранить проверку границы, лимит глубины и
категории ошибок, не вызывать функцию, предполагающую уже проверенный
диапазон, на произвольном хвосте. Блок для Object-member может оставаться
нужным для порядка вставки; это другой случай. Добавить счётчик реально
перенесённых событий и проверку семейства без Object-merge.

### R8-F2. P2: результат memo зависит от quote-mode внешнего текста

Место: `src/parser/inline.rs:1070`, `:1759`, `:1855`, `:1883`.
Пробел проверки: `src/parser/tests.rs:1920`.

Фактические результаты `parse()` и `from_str::<serde_json::Value>()`,
одинаковые в debug/release:

| Вход | Категория |
|---|---|
| `[[][text]` | `UnterminatedInlineCompound` |
| `[[]['text]` | `MalformedInlineCompound` |
| `[{}[text]` | `MalformedInlineCompound` |
| `{a: [[][text]}` | `UnterminatedInlineCompound` |
| `{a: [[][text], q: '}` | `MalformedInlineCompound` |

Все эти примеры некорректны, но различие категорий существенно. После
закрытого первого `[]` позиция значения уже потреблена; без запятой
последующий `[text` не начинает новый законный элемент. По разделам
5.8.5 и 6.12 это лишнее содержимое после закрытого compound, то есть
`MalformedInlineCompound`. Кавычка в Array scalar не является quoting
по разделу 5.3.3 и не должна задним числом менять роль предыдущего `[`.

Корень расхождения: `FindFast/ScanFast` оставляют `value_start` после
закрытия пустого Array, а `FindQ/ScanQ` сбрасывают его. Это отличие
fast от quote-aware, не возврат пяти исправленных отличий find от scan.

Новый memo добавляет зависимость от внешнего контекста. Для тела
`{a: [[][text], q: '}` внешний проход выбирает `ScanQ` и записывает
диапазон Array `(4, 12)`. `known_closer()` по одному offset считает эту
границу пригодной для ограниченного значения `[[][text]`. Но отдельный
проход по этому срезу выбирает fast-режим без кавычек и не находит closer.
Условие записи на `:1759` считает quote-aware вход автоматически чистым,
не проверяя режим, который выберет потребитель среза.

Текущий тест сравнивает memo с проходом по `&body[o..]`, то есть по
суффиксу, сохраняющему кавычку следующего поля `q`. Он не проверяет
`&body[o..=c]`, соответствующий ограниченному значению, и потому может
согласовать два quote-aware прохода вместо нужного fast-прохода.
Существующий перебор коротких тел также не содержит кавычек в алфавите.

Исправление: согласовать значение байтов в fast/quote-aware режимах,
включая потребление value-start после закрытия compound; затем проверять
memo на реальных срезах обоих потребителей, ограниченном значении и
суффиксе split. Если различия режимов сохраняются, одного opener offset
недостаточно для доказательства чистоты кэша. Нельзя исправлять это
повторным полным сканированием каждого диапазона и незаметно вернуть
старую стоимость `O(N * D)`.

### R8-F3. P2: новые dedent-тесты не вызывают owned-парсер

Место: `tests/multiline_codepoint_dedent.rs:25`,
`tests/multiline_vt_dedent.rs:23`; путь `from_str`: `src/lib.rs:159`.

Обе функции `owned_scalar()` вызывают `from_str::<Cfg>()`. Но `from_str`
использует `thin::parse_events_merged`, а соседняя функция вызывает
`parse_events`, также использующий thin `EventParser`. Owned-движок
`ktav::parse()` и его `src/parser/collecting.rs` здесь не выполняются.

Это особенно важно для новых контрпримеров U+2000/U+2001: побайтовое
сравнение общего префикса способно вернуть середину UTF-8 code point.
Возврат такой ошибки только в owned-копию helper не затронет эти новые
«проверки обоих парсеров». Речь об устройстве тестов, не о выполненной
мутации репозитория.

Внешняя проверка этого ревью вызвала настоящий `parse()` и `from_str()`
на двух Unicode-контрпримерах: текущий код даёт правильные строки. Она
не заменяет постоянную защиту в CI.

Исправление: в owned-helper использовать `parse()` и извлекать String
из `Value`; сохранить отдельные проверки `from_str` и `parse_events`.
Сравнивать каждый результат с независимым ожидаемым содержимым, а не
только друг с другом. Желательно не поддерживать три разные трактовки
общего префикса в двух парсерах и writer, см. R8-F5.

### R8-F4. P2: saturating_sub не защищает предшествующее умножение

Место: `src/parser/collecting.rs:88`, `src/thin/event_parser.rs:1762`.

Оба dedent-оценщика вычисляют `common_len * lines.len()` обычным `usize`
до передачи результата в `saturating_sub`. На 32-битной цели с включёнными
overflow checks возможен panic на корректном документе.

Конструкция входа: одна непустая строка с 65 536 пробелами перед `x` и
65 535 пустых строк внутри stripped-блока. Пустые строки не участвуют в
вычислении общего префикса, но входят в `lines.len()`:

```text
common_len = 65536
lines.len() = 65536
65536 * 65536 = 4294967296 > usize::MAX на 32 битах
```

В ревью один такой документ размером 131 083 байта разобран обоими API
на x64 в debug/release; длина результирующей String равна 65 536.
Проверка произведения через `u32::checked_mul` возвращает `None`.
Сам 32-битный target не запускался: это доказательство по арифметике
при проверенных предпосылках входа, не наблюдённый локальный panic.
Без overflow checks результат умножения оборачивается, и оценка ёмкости
тоже становится неверной, хотя это само по себе не меняет строковый Value.

Исправление: насыщать также умножение либо вычитать общий префикс только
из непустых строк, где он реально удаляется. Второй вариант точнее для
документов с большим числом пустых строк. Добавить 32-битный regression
контроль; не полагаться на наличие внешнего `saturating_sub`.

### R8-F5. P2: writer путает разные отступы с общим префиксом

Место: `src/render/helpers.rs:250`, `:283`, `:309`.

Объект со String `"\talpha\n ))"` корректно получается из stripped-ввода.
Но и `emit_canonical()` для этого `Value`, и `to_string()` для карты с
такой строкой возвращают `Unrepresentable(LeadingWhitespaceCollision)`.
Проверено в debug/release. Вариант `"\u{2000}alpha\n\u{2001}))"` даёт
тот же ложный отказ.

У первой строки ASCII-примера отступ начинается с TAB, у второй с SPACE:
общего code-point префикса нет. Сегмент ` ))` запрещает verbatim-форму,
но stripped-форма ничего из оригинального содержимого не удаляет.
Нет CR, trailing whitespace, строки `)` или общего начального code point.

Более того, проверен lossless-кандидат с каноническим внешним отступом:

```rust
"value: (\n    \talpha\n     ))\n)\n"
```

`parse()` возвращает тот же Object со строкой `"\talpha\n ))"`: удаляются
только четыре добавленных writer-пробела, а различающиеся TAB/SPACE остаются.
Так что это не вывод «всё parseable обязано быть representable»: проверены
конкретные условия отказа и существование нужной lossless-формы.

Раздел 5.9.7 запрещает этот fallback при действительно общем начальном
whitespace code point; раздел 5.6 сравнивает префикс code-point-for-code-point.
Однако `stripped_lossless` требует наличия полностью неотступленной строки
(`unindented_line`). Это достаточное, но не необходимое условие пустого
общего префикса.

Исправление: использовать реальную проверку общего префикса, согласованную
с dedent, вместо булева «все строки имеют какой-то отступ». Добавить
положительные roundtrip-оракулы для разных TAB/SPACE и Unicode-prefixes
вместе с сегментом `))`; сохранить отрицательный случай одинакового
начального SPACE на всех непустых строках.

### R8-F6. P3: memo убирает пересканы, но не даёт строго линейный индекс

Место: `src/parser/inline.rs:1072`, `:1080`, `:2354`.

Пары границ сортируются, а каждый запрос делает бинарный поиск. Для `C`
записанных compound spans и `O(C)` обращений эта часть имеет оценку
`O(N + C log C)` на обычных memo hits, где `N` есть длина inline-тела.
Это заметно лучше повторного чтения поддеревьев по глубине, но при множестве
коротких неглубоких compounds может добавлять работу по сравнению с
постоянно короткими локальными сканами.

Это не ошибка результата. Компактный отсортированный `Vec` имеет полезные
свойства памяти и может выигрывать практически. Если профиль покажет
существенную цену lookup, рассмотреть передачу уже найденного boundary ID,
последовательные представления диапазонов или адаптивный индекс с ожидаемым
`O(1)`. Не заменять его без измерений плотной таблицей на каждый байт входа:
это может ухудшить память на длинных строковых телах с малым `C`.

## Регрессия И Закрытие Работ

Переданные пользователем коэффициенты относятся к предыдущему отчёту о
фиксе на `7e5a17a`; это не замеры текущего `cdb10d1`:

| Сценарий | Переданное отношение времени |
|---|---|
| `deep_nest` | 1.127 |
| `deep_nest_arr` | 1.189 |
| `deep_nest_events` | 1.155 |
| Массовые сценарии | 0.96--0.99 |

Методика в сообщении: закрепление на ядре, шесть чередующихся раундов,
нормировка на итерацию. Эти замеры и корпус 7422 входов в данном ревью не
повторялись; из сообщения нет полного набора сырых наблюдений и baseline SHA.
Поэтому я не приписываю конкретный процент отдельному изменению кода.

Сохранять исправление известного нарушения spec вместо отката ради такого
бенчмарка обоснованно. Но соответствие spec требует правильных границ,
не их повторного вычисления на каждом уровне; 12--19% не являются
доказанной нижней границей необходимой цены. Новый memo устраняет большую
часть старого механизма #161 на успешных hits. Копирование из R8-F1 остаётся
независимой работой, которую этот memo не убирает.

оптимальности `6N + 4096` для любого распределения документов.

## Приоритеты И Вопрос

Рекомендуемый порядок: закрепить реальные owned/thin проверки; исправить
семантику и тестовые срезы memo; устранить переполнение ёмкости и ложный
writer-отказ; затем убрать копии вложенных Array и измерить оставшуюся
цену индекса. Не откатывать правильные byte semantics ради константы.
Для контроля сложности считать просмотры и переносы событий, а не только
вызовы хеш-индекса или ненормированное время процесса.

Отдельный открытый вопрос, не включённый в счёт подтверждённых дефектов:
`[:: x]` сейчас превращается в Array со строкой `x`, а `[::]` в Array с пустой
String. В §4/§5.8.3 inline items описаны через `<inline-value>`, без явно
выделенной raw-marker ветки, в отличие от array-item lines §5.4.
Нужен однозначный нормативный оракул или уточнение текста. Ранние ревью
принимали это поведение реализации как данность; оно не заменяет норму.
Не предлагаю молча менять существующий синтаксис без решения автора spec.
