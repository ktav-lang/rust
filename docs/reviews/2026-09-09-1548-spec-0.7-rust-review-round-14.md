## Найденные Проблемы

### R14-F1. P2: отсутствуют deserialize_i128 и deserialize_u128

Места: `src/thin/event_deserializer.rs:142`, `:213`, `:240`;
`src/de/value_deserializer.rs:49`, `:107`, `:124`.
Обещание API: `README.md:375`. Пробел в тестах:
`tests/ser/typed.rs`, `tests/roundtrip/typed.rs`.

Оба десериализатора реализуют целые типы только до 64 бит. Методы
`deserialize_i128` и `deserialize_u128` не переопределены. В
закреплённом serde `1.0.228` default-реализации этих методов всегда
возвращают соответственно `i128 is not supported` и
`u128 is not supported`, не проверяя входное значение.

Минимальный воспроизводитель:

```rust
let back: Vec<u128> = ktav::from_str("1\n").unwrap();
assert_eq!(back, vec![1]);
```

Вызов возвращает `Err(Message("u128 is not supported"))`, поэтому
`unwrap` падает. Для `Vec<i128>` и `-1` результат аналогичен.
`de::from_value`, даже получив успешно разобранный `Value`, возвращает
ту же ошибку. Проблема не связана с i64-overflow классификацией:
минимальные примеры находятся внутри домена parser Integer.

Проверены bare/raw Object-поля, положительные и отрицательные значения,
`u128::MAX`, `i128::MIN`, `i128::MAX` и Array roots. Все 18 ожидаемых
успешных чтений через `from_str` / `de::from_value` отвергаются в
debug/release. Отдельный assertion успешного чтения действительно
падает; эти проверки не включены в число passed штатных тестов.

README перечисляет `u8..u128` и `i8..i128`, а затем обещает чтение
числового тела в целевой тип. Serializer уже пишет 128-битные числа
целиком, включая края диапазона. Существующие тесты проверяют эти
байты, но не составляют такой результат с обратным чтением в
128-битный тип. Поэтому штатный зелёный прогон пропускает дефект.

Исправление: реализовать оба метода в обоих десериализаторах через
существующее извлечение numeric/string text и точный `parse::<i128>` /
`parse::<u128>`, затем `visit_i128` / `visit_u128`. Не прогонять их через
64-битный промежуточный тип или `f64`. Сохранить ошибки переполнения,
отрицательного unsigned и нечислового текста. Добавить полные
serde-roundtrip для Object/Array и owned/thin, отдельные проверки
`::`, MIN/MAX и соседних значений вне диапазона. Это потребительская
типизация; расширять нормативный Integer-домен parser для неё не нужно.

### R14-F2. P2: serde-to-Value допускает Integer, который parser считает String

Места: `src/ser/value_serializer.rs:20`, `:89`, `:101`, `:104`;
`src/render/representable.rs:65`; `src/parser/classify.rs:99`, `:214`;
публичный сценарий: `src/ser/mod.rs:5`.

`ValueSerializer` всегда оборачивает вывод `itoa` в `Value::Integer`,
включая `u64`, `u128` и `i128` за пределами i64. Parser реализует
минимальный Integer-домен из §5: такие же десятичные литералы вне
i64 становятся String. Writer не обнаруживает несогласованность и
выдаёт успешный результат как для обычного Integer.

Воспроизводитель не создаёт некорректный `Value` вручную:

```rust
let source = std::collections::BTreeMap::from([("x", u64::MAX)]);
let before = ktav::ser::to_value(&source).unwrap();
let text = ktav::emit_canonical(&before).unwrap();
let after = ktav::parse(&text).unwrap();
assert_eq!(after, before);
```

`before` содержит `Integer("18446744073709551615")`, а `after`
содержит `String("18446744073709551615")`. Первый canonical output:

```ktav
x: 18446744073709551615
```

После parse и повторного canonical emit:

```ktav
x:: 18446744073709551615
```

Таким образом, меняются и вариант Value, и canonical bytes. `render`
имеет тот же эффект; Array root также затронут. Подтверждены
`(i64::MAX as u128) + 1`, `(i64::MIN as i128) - 1`, `u64::MAX`, `u128::MAX`,
`i128::MIN` и `i128::MAX`. Контрольные границы i64 сохраняются.
Всего 26 расхождений в 34 сочетаниях value/root/writer, одинаково
в debug/release; обязательный assertion равенства падает.

Десятичные цифры не теряются. В частности, прямой
`to_string -> from_str::<...u64>` для `u64::MAX` проходит. Это отличает
R14-F2 от R14-F1: здесь нарушается динамическая модель документа,
даже когда потребительский Rust-тип поддерживается. Реализация
128-битных методов чтения сама по себе этот дефект не устранит.

Нельзя считать сам fallback parser ошибкой спеки: §5 и §5.2 rule 13
разрешают минимальный i64-домен; fixture `i64_overflow_to_string`
требует именно String для такой реализации. Несогласован мост из
serde в Value: он допускает Integer шире того же parser-домена,
а публичный двухшаговый путь предлагается для обработки документов.

Исправление требует явной политики на границе `ser::to_value`:
при сохранении i64-домена не создавать неподдерживаемый Integer
молча, а согласовать ошибку либо документированное преобразование в
String. Альтернатива состоит в осознанном расширении домена одновременно
для parser/writer/декларации и boundary-oracles, не в одиночной замене
проверки parser, ломающей минимальный conformance corpus. Закрепить
`to_value -> writer -> parse` и повторный canonical emit на обеих
границах; не заменять сравнение Value только проверкой цифр.

### R14-F3. P3: исправленные ссылки не исправили устаревшее содержание docs

Места: `README.md:367`, `:396`, `:400`;
`README.ru.md:358`, `:388`, `:392`;
`README.zh.md:339`, `:366`, `:370`;
`src/thin/event_deserializer.rs:1`, `:5`.

В README остаются два неверных описания текущего parser:

- В примере `name: Russia / port: 20082` результат показан как
  `port: "20082"`, а ниже сказано, что все скаляры на Value-уровне
  являются строками. Публичный `parse` даёт `Integer("20082")`;
  String остаётся только `name`. Типовая классификация §5.2 уже
  реализована в коде, но примеры и текст описывают прежнюю модель.
- Для `parse_events` обещана внешняя Object-пара у любого документа.
  Проверенный `[1, 2]` выдаёт `BeginArray`, два `Integer`, `EndArray`,
  без внешнего Object. Это корректно по §5.0.1, неверен текст README.

Оба противоречия присутствуют в EN/RU/ZH. Результаты коротких публичных
воспроизводителей совпали в debug/release.

В модульном rustdoc `event_deserializer` ссылки теперь заменены
code spans, но утверждение о generic `EventSource` и используемом
`StreamingParser` без буфера всего документа осталось. На деле
`EventDeserializer` содержит конкретный `EventCursor`, а
`src/lib.rs:176` сначала полностью получает events через
`parse_events_merged` и лишь затем вызывает десериализацию.
Это не on-demand источник; комментарий ниже в том же модуле даже
объясняет прежний отказ от такого источника. Устаревший заголовок
вводит в заблуждение при оценке памяти и выборе архитектуры.

Исправление: синхронизировать содержимое README в трёх языках с
действующими типами/root kinds и обновить внутреннее описание до
реального slice cursor. Примеры классификации и event root закрепить
обычными integration-тестами. Новый deny-lint правильно защищает
ссылки, но не способен проверить истинность документации. Это P3
документационный долг, не runtime-регрессия последних исправлений.

## Закрытие Раунда 13 И Производительность

**R13-F1 закрыт.** `float_scalar_f32` получает shortest decimal Ryu-f32,
читает его как f64 и сохраняет Ryu-f64 payload. Это согласовано с
parser и не заменяет прежнюю decimal-политику расширением `v as f64`.
`expect` здесь обоснован: после отсева non-finite любой результат
Ryu-f32 есть корректный конечный литерал в пределах f64.

Прежний внешний набор из 23 f32 x 2 root x 2 writer теперь проходит
с обязательным равенством Value: **0 расхождений из 92** в обоих
профилях вместо 32. Числовые биты сохраняются; 46 canonical outputs
принимаются strict parser и идемпотентны. Новые три integration-теста
покрывают оба знака и границы notation, дополнительно проверяют биты,
strict acceptance и точные canonical bytes. Прежние 13 f64 случаев
также прошли, включая subnormal, крайнее конечное число и signed zero.

**R13-F2 закрыт.** Обе сборки rustdoc, включая private items, прошли
без warnings. В crate включён `deny(rustdoc::broken_intra_doc_links)`.
Он сработает при сборке документации, а не заменяет её запуск в CI.
R14-F3 относится к смыслу оставшегося текста, а не к разрешению ссылок.

Два Ryu buffer в f32 helper остаются стековыми; промежуточный heap
`String` не возвращён. Новый parse/format добавляет постоянную работу
на число фиксированной разрядности, а не меняет асимптотику. Для G
Float остаётся `O(G)`; оснований жертвовать корректной нормализацией
ради непроверенного fast path нет. Проценты выигрыша или замедления
не измерялись.

Сохраняются ранее отмеченные профильные кандидаты, не новые находки:
две временные строки scientific-ветки `canonical_float`,
`O(C log C)` компонент индекса C inline-границ и предварительный
резерв arena от длины исходника. Убрать временный результат
`normalise_scientific` можно отдельной оптимизацией с сохранением
точных байтов, signed zero, strict diagnostics и порогов notation.
Менять индекс или arena policy без профиля в этом раунде оснований нет.
Multiline `Vec` не возвращён; нагрузочные/allocator-измерения не запускались.
