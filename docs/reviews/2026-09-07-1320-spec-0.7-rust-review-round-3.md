# Ревью Rust-реализации Ktav spec 0.7, раунд 3

Дата: 2026-09-07.

Rust commit: `3f1fabbc6085d6bbb2df0bb25e6fce499794dcd8`.
Spec submodule: `7f05a1b39a773d22f5e9a927d7c55c8c51d82de4`.
Предыдущий отчёт: `docs/reviews/2026-09-07-1140-spec-0.7-rust-review-round-2.md`.

## Вердикт

**NO-GO: один P1 и три P2.** Все четыре findings раунда 2 закрыты на своих
репродьюсерах; появились прямые corpus-проверки результатов `from_str()`.
Однако общий inline scanner по-прежнему паникует на допустимом trailing
comma с whitespace, отвергает quoted keys внутри array-contained Objects и
принимает структурно некорректный ввод, ошибочно скрывая разделители внутри
значений. Оба parser API используют этот код и воспроизводят одинаковые ошибки.

Штатные проверки зелёные: 843 теста в каждом из debug/release профилей,
9 conformance-тестов, fmt и Clippy. Новые короткие воспроизводители проверены
отдельно в обоих профилях, без изменения production-кода и repository tests.

## Findings

### R3-F1. P1: whitespace после trailing comma вызывает выход за границы

Место: `src/parser/inline.rs:915-942`, `split_top_level()`.

Воспроизводитель:

```ktav
{"a": 1, }
```

Документ валиден: §5.8 разрешает trailing comma, §5.8.1 разрешает whitespace
внутри inline compound. Ожидается Object с единственной парой `a = Integer(1)`.

И `parse()`, и `from_str::<serde_json::Value>()` паникуют:

```text
src/parser/inline.rs:942:15
index out of bounds: the len is 8 but the index is 8
```

Вариант без пробела `{"a": 1,}` успешно разбирается. Tab после запятой даёт
тот же panic. Ошибка также воспроизводится во вложенной форме
`outer: {"a": 1, }`. На некорректном `{ "a": 1, b. }` также получается
panic вместо структурированной ошибки.

Причина: после запятой scanner устанавливает `in_key/seg_start`, затем
`skip_segment_ws()` может довести `i` до `bytes.len()`. После проверки
возможной кавычки код продолжает выполнение и обращается к `bytes[i]`.
Проверка границы в начале while больше не достаточна после изменения `i`.

Исправление: проверить EOF после пропуска whitespace и корректно завершить
последний пустой segment для trailing comma. Нужны tests для SPACE/TAB,
Unicode whitespace, quoted keys и quotes в значениях, root/nested форм.
Такую же последовательность skip-then-index следует проверить в остальных
scanner helpers.

### R3-F2. P2: quote tracking зависит от внешнего opener, а не текущего вложенного Object

Места: `src/parser/inline.rs:1042-1075` (`find_matching_close`),
`:1257-1388` (`scan_inline_closer`).

Валидные документы:

```ktav
[{"x]y": 1},2]
```

```ktav
[{"x}y": 1},2]
```

Ожидаются два Array item: Object с буквальным quoted key и Integer(2).
Quoted key допускает скобки по §5.3.3; они не должны закрывать контейнер.
Оба API вместо этого возвращают `UnterminatedInlineCompound` на первой строке.
Также воспроизведено в pair value:

```ktav
a: [ {"x]y": 1} ]
```

Причина: `track_quotes` вычисляется по внешнему `open == '{'`. Если внешний
compound является Array, scanner выбирает fast path, который не становится
quote-aware при входе во вложенный Object. Байт `]` или `}` внутри ключа
изменяет глубину как настоящий closer.

Исправление: отслеживать тип и key/value позицию каждого вложенного scope.
Array не поддерживает quoted scalar values, но его Object-элементы имеют
полноценные quoted keys. Покрыть оба вида скобок, оба outer container kind,
разные delimiters quoted key и последующий sibling item.

### R3-F3. P2: value quotes ошибочно защищают структурные closers

Места: `src/parser/inline.rs:1428-1438`;
ошибочный regression oracle: `src/parser/tests.rs:549-550`.

Воспроизводитель:

```ktav
{x: "a}b"}
```

По §5.3.3 quoting применяется только к key segments. В inline scalar
кавычка является обычным символом. Первый неэкранированный `}` завершает
внешний Object; хвост `b"}` делает документ некорректным.
На текущем коде оба API успешно возвращают String со всеми байтами `"a}b"`.

Причина: ветвь `value_start && is_quote_byte(bytes[i])` пропускает целый
quote-delimited span, включая структурные скобки. Её комментарий прямо
приписывает quoted values opacity, которой спецификация не даёт.

В собственном unit test уже закреплена неверная предпосылка:
`assert!(parse("{a: \"x] y\", b: 1}").is_ok())`.
Поэтому простое сохранение зелёных существующих tests может сохранять баг.

Исправление: убрать value-side quote opacity; сохранить её исключительно
для quoted key segments. Для буквальной скобки внутри inline String должен
использоваться предусмотренный escape. Проверять отрицательный unescaped
пример и положительный escaped пример на обоих API.

### R3-F4. P2: сбалансированные скобки посреди скаляра скрывают запятые и closers

Места: `src/parser/inline.rs:959-970`, `:1004-1009`
(`split_top_level` / fast variant), `:1340-1361` и `:1488`
(`scan_inline_closer`).

Воспроизводитель:

```ktav
{a: x{y,z}, b: 2}
```

Текущий результат обоих API:

```text
Object { a: String("x{y,z}"), b: Integer(2) }
```

Но §5.8.5 выбирает compound или scalar ровно по первому непробельному
символу значения. Значение начинается с `x`, поэтому `{` посреди него
является литеральным символом и не открывает вложенный scope. Следующая
запятая завершает scalar; последующий segment `z` не является Object pair.
Документ должен быть отвергнут, а не превращён в String с неэкранированной
запятой внутри.

Аналогично оба API принимают `{a: x[y,z], b: 2}` с целиком сохранённым
`x[y,z]`, хотя внутренний `[` не должен начинать compound.

Причина: scanner ищет matching closer для mid-scalar opener и пропускает
весь сбалансированный фрагмент. Для настоящего value-start compound это
правильно; для mid-scalar литерала такой skip меняет роль разделителей.
В `scan_inline_closer()` это даже отдельная ветвь для opener вне value start.

Исправление: использовать единые правила scalar/compound state при поиске
closer и при разделении pairs/items. Mid-scalar opener не даёт права
пропускать запятые или closers. Сохранить положительный пример спецификации
`{a: hello{world, b: x}` и добавить отрицательные случаи со случайно
сбалансированными скобками и положительные случаи с escapes.

оба пути могут одинаково наследовать ошибочное распознавание.

## Качество реализации и улучшения

После раунда 2 заметно улучшилось покрытие: проверяется конечный результат
Serde, числовой kind и знак Float-ноля, категории invalid errors и
комбинации nested compounds с re-entry. Это полезные проверки внешнего
контракта, а не только внутреннего состояния parser.

Следующий приоритет: согласовать три overlapping helpers
`scan_inline_closer`, `find_matching_close`, `split_top_level` вокруг одной
модели scope/key/value/quoted-key/raw-scalar. Сейчас их разные shortcuts
дают как ложные отказы, так и ложное принятие некорректного документа.
Новые tests должны исходить из §5.3.3 и §5.8.5, особенно при исправлении
уже неверных положительных assertions.

Рекомендация раунда 2 по сложности остаётся актуальной:

- `src/thin/merge.rs:21` заявляет O(n), но `find_seen()` на `:222` линейно
  ищет каждый Object key. Для k разных sibling Objects возможны
  k(k-1)/2 сравнений.
- `src/thin/event_parser.rs:898` и `:1071` линейно ищут paths. Новый fold
  child paths на `:1285-1300` дополнительно копирует полные segment chains
  в ancestor tables; большой depth увеличивает объём повторных копий.

Это статическая оценка алгоритмов. Бенчмарки/стресс-нагрузки не запускались,
количественные latency/RAM claims не делаются. После semantic fixes стоит
рассмотреть индекс по decoded paths или prefix tree с insertion order и
проверить обычные wide-object/nested-object workloads.

## Область и ограничения

Проверены изменения `21623ce..3f1fabb`, новый child-path fold, merge,
root tuple-variant guard и runner. Дополнительно проверены shared inline
scanner helpers против локальной spec 0.7, поведения quoted keys, comma и
closer precedence. Старые root/dotted-key примеры и новые комбинации
проверялись через публичные API.

Это целевое ревью 0.7 и новых правок, не исчерпывающий аудит всех входов,
зависимостей и target-платформ. MSRV 1.71, Linux/macOS, Miri, supply-chain
audit и remote CI в этом раунде не запускались. Версия crate/spec metadata
остаётся `0.6.4` согласно принятому README-статусу подготовки draft 0.7;
version bump не выполнялся.

Рабочее дерево оставалось чистым до создания отчёта. Production-код и
repository tests не изменены. Единственный файл для коммита по запросу
пользователя: настоящий Markdown-отчёт. Push не выполнялся.
